## 一、产品愿景

**冰美商城 (IcedAmericanoMall)** 是 B2B2C 模式的电商平台，类似淘宝/京东。目标是打造一个集用户购物、商家运营、平台管理于一体的分布式微服务电商系统。

**核心理念**：结合业界主流技术方案与大型互联网公司的工程实践，探索个人全栈开发的最佳路径。不追求空洞的「高可用」「高并发」口号，而是用**技术方案 + 量化结果 + 业务价值**说话。

### 目标特性（量化指标）

| 特性   | 目标                          | 衡量方式                 |
| ---- | --------------------------- | -------------------- |
| 高并发  | 峰值 12000 TPS，P99 延迟 < 500ms | 压力测试报告               |
| 易维护  | 配置变更无需重启，发布频率从周级→日级         | Nacos 配置中心 + 自动化部署   |
| 稳定性  | 电商大促期间零故障                   | 故障记录                 |
| 可扩展性 | 用户量从 10 万→1000 万无需重构        | 架构评审                 |
| 可观测性 | 故障定位从小时级→分钟级                | Prometheus + Grafana |
| 安全性  | 满足等保 2.0 要求                 | 安全审计                 |

## 二、用户角色

| 角色        | 描述                    | 典型行为                       |
| --------- | --------------------- | -------------------------- |
| **游客**    | 未登录用户                 | 浏览商品、搜索、查看商品详情             |
| **普通用户**  | 已注册登录用户               | 下单支付、积分签到、收藏、管理地址          |
| **商家**    | 拥有店铺的用户（一个用户只能成为一个商家） | 管理商品、处理订单、发货、查看数据          |
| **管理员**   | 平台最高权限                | 管理用户/商家/商品/订单、营销配置、数据统计    |
| **第三方系统** | 外部服务                  | 支付网关（微信/支付宝）、短信服务、OSS 对象存储 |

### 登录策略（完整支持，逐步实现）

- 单地登录 / 多地登录 / 多端登录 / 单端登录 / 同端互斥登录
- 七天免登录
- 空闲超时：半小时无操作后需重新登录

### 3.13 买家-商家消息系统（V3.3 ✅）

> **大厂对标**: 淘宝旺旺（独立消息系统 + 店小蜜嵌入）+ 京东咚咚（JIMI客服嵌入IM）。
> 大厂把买家-商家 IM 定位为**独立消息系统**，AI 是嵌入在消息系统中的**辅助能力**（商家离线/繁忙时自动代答）。

#### 消息系统（基础设施）

| 功能 | 阶段 | 说明 |
|------|------|------|
| WebSocket 长连接 | ✅ V3.3 | gateway-service 统一 WebSocket 入口，STOMP 子协议，心跳保活 |
| 买家-商家实时消息 | ✅ V3.3 | 商品详情页/订单列表页发起对话，消息已读/未读状态，conversation_id 会话隔离 |
| 消息持久化 | ✅ V3.3 | `chat_message` 表 MySQL 存储 + Redis 最近 100 条热缓存，分页查询历史 |
| 离线消息推送 | ✅ V3.3 | RabbitMQ 延迟队列 → WebSocket 推送 → App 通知栏 |

#### 店铺 AI（嵌入消息系统）

| 功能 | 阶段 | 说明 |
|------|------|------|
| 商家知识库管理 | ✅ V3.3 | 商家后台上传 FAQ/政策/产品手册 → `merchant_knowledge_base` 表 → ES 索引 |
| 商家 AI 自动代答 | ✅ V3.3 | 仅检索本店知识库（非全平台），复用 `CustomerServiceAssistant` + `RAGRetriever` |
| 商家对话模板 | ✅ V3.3 | `merchant_reply_template` CRUD：欢迎语/离线回复/FAQ 模板/快捷话术 |
| 人机转接通知 | ✅ V3.3 | AI 置信度 < 0.7 → 消息系统内通知商家（非独立工单系统） |

**技术方案**：
- **消息系统**: WebSocket + STOMP + RabbitMQ（与 AI 服务解耦，独立演进）
- **店铺 AI**: 复用 `ai-service` 现有 `CustomerServiceAssistant`，限定检索范围为 `seller_id` 的知识库
- **对话模板**: 商家后台 CRUD → RAG 检索时优先匹配模板 → 模板命中直接返回，不调 LLM（省成本）
- **知识库隔离**: 商家只能管理本店知识库，RAG 检索时过滤 `seller_id`

- **多维度SKU**: `sku_spec_dimension`(维度名)/`sku_spec_option`(选项值) 表 + `spec_json` 字段
- **原价/到手价**: sku 增加 `original_price`，详情页显示"¥到手价 ~~¥原价~~"
- **立即购买**: `POST /api/trade/order/direct { skuId, quantity, addressId, couponId? }` 跳过购物车
- **关注商家**: `store_follow` 表 + `POST /api/shop/follow/{sellerId}`
- **评论增强**: `media_urls` JSON(图+视频URL) + `GET .../filter?rating=5&hasMedia=true&sort=newest`

    And 验证码从 Redis 中删除

  Scenario: 重复手机号注册
    Given 手机号 "13800138000" 已被注册
    When 用户提交注册请求
    Then 返回错误 "手机号已注册"

    Given 手机号 "13800138000" 未被注册

    Given 用户已成功注册

## 八、V5.8 增量需求要点（P1：F5 促销引擎 / F6 会员等级）

### F5 店铺满减/满折促销（营销域 + 交易定价中心）

- **需求**：管理端可创建店铺级满减/满折活动；买家下单时自动应用最优活动，优惠与会员折扣、优惠券可叠加（同类型促销不叠加，取减免最大者）。
- **核心场景（BDD）**：
  - Given 店铺有满 300 减 40 活动，When 购物车商品总额 350 下单，Then discountAmount=40、payAmount=310+postFee
  - Given 同时命中满 300 减 40 与满 200 减 30，When 下单，Then 取减免最大者 40（同类型不叠加）
  - Given 满折 8.5 折封顶 100 元、商品总额 400，When 下单，Then 减免 = min(400×15%, 100) = 60 元
  - Given 商品总额低于门槛，When 下单，Then 不应用该活动（合法业务态，不报错）
  - Given marketing 不可用，When 下单，Then 下单失败（fail-closed，促销不静默失效）
- **Phase 2（roadmap）**：C 端商品页促销标签、N 元 N 件、多活动叠加策略、商品级 scope、多券分摊（开放项 O1）。

### F6 会员等级升降级与权益（用户域 + 交易接线）

- **需求**：买家按累计实付金额（成长值）自动升级会员等级（Phase 1 只升不降），等级带来**会员折扣率**（下单计价）与**积分倍率**（下单奖励积分）两项权益。
- **核心场景（BDD）**：
  - Given 累计实付达 5000 元（GOLD 门槛），When 新订单确认收货，Then 等级升为 GOLD，且成长值流水幂等（同订单号仅入账一次）
  - Given GOLD 会员（98 折），When 下单 200 元商品，Then 会员优惠 4 元计入 discountAmount
  - Given GOLD 会员（1.2 倍积分），When 确认收货实付 100 元，Then 奖励积分按 1.2 倍计算
  - Given user-service 不可用，When 下单，Then 下单成功但按无会员折扣计价（fail-open + 告警）
- **Phase 2（roadmap）**：年度降级考核、运费券/专属客服等权益扩展、管理端等级规则编辑、成长值补账任务。

## 九、V5.9 增量需求要点（P2 第一批：F7 商品向量推荐）

### F7 相似商品推荐（复用 T14 向量管道）

- **需求**：商品详情页展示「相似推荐」——基于商品向量化（名称+描述）的 kNN 相似检索，返回在售商品卡片；用户无感知降级（推荐缺失不报错）。
- **核心场景（BDD）**：

  - Given 商品编辑（名称/描述变更），When 保存，Then 向量幂等覆盖写，后续推荐反映新内容
  - Given 商品已下架，When 组装推荐卡，Then 不出现在结果中（item 侧恒过滤在售）
  - Given ES 或 Embedding 未启用，When 访问推荐位/保存商品，Then 推荐返回空列表、摄取静默跳过（0），主流程零影响
  - Given search-service 不可用，When 保存商品/访问推荐位，Then Feign 降级（哨兵 -1/空列表），主流程零影响
- **Phase 2（roadmap）**：「看了又看」（浏览共现统计）、多路召回与排序、推荐位 CTR 埋点、首页推荐流。

  - Given 团 1/3，When 用户 B 参团支付成功，Then 团 2/3；用户 B 重复参同团 → 拒绝（uk_team_user）
  - Given 团 2/3，When 用户 C 参团支付成功，Then 团满员置「已成团」，订单走正常发货流程
  - Given 团 2/3 且超过成团时限，When 结团任务扫描，Then 团置「已失败」，A/B 的订单逐单「取消 + 恢复库存 + 全额原路退款」，退款成功买家收站内信
  - Given 团 2/3，When 用户 C 支付成功但团恰好已被填满（竞态），Then C 的参团失败 → 订单自动取消并全额退款
  - Given 活动不在进行中/团不存在/团已满，When 用户下单，Then 400 拒绝（下单不占团位，未支付订单走既有 30 分钟超时取消）
  - Given 同一订单号，When 退款指令重放，Then 幂等返回既有退款单（biz_ref 锚点）
- **Phase 2（roadmap）**：虚拟团/机器人成团、团成功站内信、多件购买、拼团价与券叠加、MQ 事件化、退款失败补偿任务。

### 15.1 背景与目标

**背景**：

1. **合规刚需**：消费者索要购货凭证时经营者必须出具（消费者权益保护相关规定）。C 端"订单完成后索要发票"是电商平台的基础合规能力，当前平台完全缺失（57 张表、240 端点无一涉发票）。
2. **售后联动缺口**：退款资金流已闭环（售后退款 ADR-035/037、拼团结团退款 ADR-049，`refund_order` 三通道原路退回），但"退了钱、票还在"构成虚开风险——发票必须与退款**资金终态**联动冲红/作废。
3. **B 端报销诉求**：企业买家（团队采购）需要抬头+税号的电子普票用于报销，平台无入口即流失 B 端客单。
4. **从未立项**：INV1-INV3 仅存在于 05 §4.15 V5.0 规划占位（⚪ 未实现，已挂账 roadmap），无 PRD、无数据模型、无契约定稿——本节补齐第一段。

**大厂对标**：

| 平台 | 模式 | 对本项目的启示 |
| ---- | ---- | -------------- |
| 淘宝/天猫 | **商家开票**：买家提交申请与抬头 → 商家用开票工具开具 → 买家下载；平台只提供申请/流转/提醒管道 | B2B2C 同构：销售主体=商家 |
| 京东 | 自营=**平台开票**（下单选抬头、完成后自动开具）；POP 入驻商家=商家开票 | 本平台无自营线，平台开票不适用 |
| 拼多多 | 商家开票为主，超时未开可催开 | 催开机制是买家侧标配 |

**目标**（Phase 1，模拟开具环境）：

- G1 买家可对**已完成**订单申请/查看/下载/换开电子普通发票（个人/企业抬头）；
- G2 全额退款资金终态**自动**联动冲红/作废，消除"退钱留票"虚开风险；
- G3 管理端可开具/作废/冲红/导出，形成可审计的发票处理闭环；
- G4 状态机、金额口径、幂等锚点、PII 口径按真实业务建模——Phase 2 接税局时仅替换"开具"防腐适配器，不推翻模型。

#### D1 开票主体：平台统一开票 vs 商家开票

| 选项 | 说明 | 评估 |
| ---- | ---- | ---- |
| A 平台统一开票 | 平台作为销售主体对买家开票，再与商家二次结算（京东自营模式） | ❌ 本平台是纯平台 B2B2C：销售主体=商家（`orders.seller_id`；货款经商家结算域提现，平台不经手货权），平台开票与销售主体不符，税务上不成立 |
| **B 商家开票（推荐）** | 销售主体=商家，发票以商家名义开具；平台提供申请/流转/触达/导出管道（淘宝/天猫/拼多多主流模式） | ✅ 与 B2B2C 定位、既有结算模型一致；大厂对标同构 |
| C 混合（自营平台开 + 入驻商家开） | 双轨并行 | ❌ 平台无自营线，Phase 1 不引入 |

**推荐 B**。补充口径：Phase 1 处于**模拟开具**环境（无税局对接、无法律效力票据），"开具"动作由**平台管理端集中代办**（角色占位，替代商家税务操作）；Phase 2 真实开票时升级为**商家自助开票工作台**（商家端入口），管理端保留兜底/异常处理。即：**开票主体（商家名义）Phase 1 定稿，开票操作者（管理端代办 → 商家自助）分两阶段演进**。

#### D2 票种范围与开票方式

| 选项 | 说明 | 评估 |
| ---- | ---- | ---- |
| **A Phase 1 电子普通发票（模拟开具）+ 个人/企业抬头（推荐）** | 模拟环境跑通全状态机；Phase 2 增值税专用发票 + 税局（电子发票服务商）对接 | ✅ INV1 占位报文 `{orderNo, type: PERSONAL\|COMPANY, ...}` 即普票口径；模拟开票足以验证全部产品逻辑 |
| B Phase 1 直接做专票 | 购方需地址电话/开户行账号等完整要素 | ❌ 专票必须真实税控才具抵扣效力，模拟无意义；要素复杂度放大 Phase 1 交付面 |
| C Phase 1 只做个人抬头 | 砍掉企业抬头 | ❌ 企业抬头是 B 端报销刚需（G1），且占位契约已含 COMPANY |

**推荐 A**。模拟开具 = 本地模拟开票适配器生成**简化 PDF 样票**（水印"样票"、非税务效力）存 MinIO + 生成模拟票号；真实票号/版式 Phase 2 由服务商返回。

#### D3 开票金额口径（必须精确定义）

| 选项 | 口径 | 评估 |
| ---- | ---- | ---- |
| **A 开票金额 = 实付 payAmount（推荐）** | = totalAmount − discountAmount + postFee，**含运费、扣优惠** | ✅ 与 04-Data-Model §3.7 金额不变式 V2 逐字对齐；消费者实际支付多少开多少 |
| B = totalAmount（商品价合计） | 优惠部分也开给消费者 | ❌ 平台/商家承担的优惠未实际收款，虚增税基；且与退款金额（≤ payAmount）对不齐，冲红闭环断裂 |
| C = 商品价不含运费 | 运费另行处理 | ❌ 运费属价外费用应并入开票额；拆两个金额徒增争议与对账成本 |

**推荐 A**，边界细则：

- 运费**计入**（`postFee` 快照；秒杀单 `postFee=0` 天然成立）；
- 优惠（优惠券/促销/会员折扣，`discountAmount`）**不计入**——未实际支付；
- 金额在申请时从 `orders` 快照进 `invoice.amount`，订单后续任何变更不影响已申请发票（快照原则，对齐"地址/商品快照"数据约束）；
- 拼团单（ADR-049）`discountAmount=0`（拼团价直接快照进订单），开票金额 = payAmount 自然成立；
- 售后退款金额既有校验 ≤ payAmount，全额退款金额恰等于开票金额——全额冲红金额对得齐。

#### D4 退款联动（冲红规则）

| 子决策 | 选项 | 推荐 |
| ------ | ---- | ---- |
| 全额退款 | A 自动冲红/作废（已开具 → 自动冲红；待开具 → 自动作废）vs B 管理端人工冲红 | **A 自动**——"退了钱票还在"是虚开合规风险，人工必漏；自动化把风险收敛进资金终态事件 |
| 部分退款 | A 自动按退款金额开部分红字 vs B 人工处理 | **Phase 1 选 B（简化口径，明确写出）**：部分退款**不**自动红字，发票保持"已开具"并置"部分退款待人工处理"标记，管理端筛选后人工冲红/换开；Phase 2 再按退款金额精确部分红字（红字信息表口径） |
| 触发锚点 | 何种事件触发联动 | **仅资金终态**：退款单成功 / 售后单回写 REFUNDED(5)（ADR-035 条件回写口径）/ 拼团结团退款成功（ADR-049，`GB:{orderNo}` 幂等锚点）。审核中/退款处理中**不**触发 |
| 冲红幂等 | 重复触发 | 已冲红的重复触发 = **幂等空操作**（不重复生成红字记录），对齐 I42 条件回写风格 |

**推荐理由（部分退款简化）**：真实部分红字需按金额拆负数票且各税局口径不一，模拟环境收益低；Phase 1 票量可控（新功能灰度期），人工处理成本可接受。**风险已知**：人工依赖存在漏处理可能——管理端列表必须提供"待人工处理"默认筛选视图，Phase 2 闭环。

#### D5 一单多票？

| 选项 | 说明 | 评估 |
| ---- | ---- | ---- |
| **A 一单一票，换开 = 冲红重开（推荐）** | 任一时刻一订单至多一张**有效**发票（待开具/已开具）；改抬头/改类型走"换开"：原票冲红 + 新票生成（关联原票） | ✅ 幂等锚点清晰（唯一约束兜底）；淘宝/京东 C 端主流即一单一票；换开语义完整覆盖改票诉求 |
| B 一单多票 | 按商品行拆分抬头/金额 | ❌ 金额分摊规则复杂（与《多券金额分摊规则》同级别的开放问题），低频诉求不值得 Phase 1 承担 |

**推荐 A**。数据面以 `uk(order_no, active_flag)` 唯一约束实现"一单一有效票"（利用 MySQL 唯一索引多 NULL 特性，同 04 §3.12 `user_auth` 先例）。

#### D6 开票时间窗

| 选项 | 说明 | 评估 |
| ---- | ---- | ---- |
| **A 仅"已完成"可申请 + 完成后 N 天内（推荐，N 默认 90，见 O1）** | 起算点 = `orders.end_time`（确认收货时间，代码已核实：确认收货 3→4 条件更新并落 `end_time`）；逾期入口关闭，管理端仍可补开 | ✅ 未完成订单退款/取消率高，先开后冲浪费；限期收敛长尾虚开敞口 |
| B 支付成功即可申请 | 票随货开 | ❌ 未发货即开票，取消/退款率放大冲红量 |
| C 完成后不限期 | 永久可开 | ❌ 长尾虚开合规敞口不可控 |

**推荐 A**。N=90 天为业界常见默认（京东支持订单完成后长期限补开、淘宝按店铺配置），具体数值列开放问题 O1 由业务裁决。

#### D7 发票能力落位（工程决策，影响产品边界）

| 选项 | 说明 | 评估 |
| ---- | ---- | ---- |
| **A 落 trade-service（推荐）** | 订单/售后/退款联动同域：金额快照读 `orders`、退款终态事件就近触发冲红，无跨服务回写 | ✅ 联动是本功能的核心复杂度，就近消灭分布式一致性成本 |
| B 新建 invoice-service | 独立微服务 | ❌ 单功能新增服务（Feign/网关/部署面膨胀），与联动需求不匹配；未来票量大再拆（内容笔记 content 分包先例，ADR-048） |
| C 落 user-service | 用户资料域 | ❌ 与退款联动最远 |

### 15.4 功能需求与状态机

#### 15.4.1 发票单状态机

状态定义（`InvoiceStatusEnum`，终态 2 个）：

| 状态 | 值 | 进入方式 | 允许的迁出 |
| ---- | - | -------- | ---------- |
| 待开具 PENDING_ISSUE | 1 | 买家申请成功 | → 已开具（开具）；→ 已作废（买家撤回 / 全额退款守卫自动作废 / 管理端作废） |
| 已开具 ISSUED | 2 | 开具成功（模拟，管理端触发） | → 已冲红（全额退款自动 / 管理端冲红 / 换开前置） |
| 已冲红 RED_FLUSHED | 3 | 冲红成功（生成红字记录） | 终态 |
| 已作废 VOIDED | 4 | 作废成功 | 终态 |

迁移语义（条件更新口径，契约阶段按 05 §九 状态机表格同款定稿）：

| 迁移边 | 触发方 | 条件更新语义（0 行 = 状态冲突） |
| ------ | ------ | ------------------------------ |
| 1→2 开具 | 管理端 | `UPDATE invoice SET status=2, issue_time=?, mock_invoice_no=? WHERE invoice_no=? AND status=1` |
| 1→4 作废 | 买家撤回 / 全额退款守卫 / 管理端 | `AND status=1`；撤回与退款守卫并发时先到先得，后到 0 行按幂等收敛 |
| 2→3 冲红 | 全额退款自动 / 管理端 / 换开前置 | `AND status=2`；已冲红的重复触发 = 幂等空操作 |

**守卫清单**：

1. **已开具不可作废**——只能冲红（防"作废已开票"的合规漏洞）；
2. 已冲红/已作废为终态——不可再开具、不可再冲红（重复触发幂等空操作）；
3. 换开仅对"已开具"有效；原票冲红（2→3）与新票创建（1）在**同一本地事务**（trade 同库，无跨服务）；
4. 全额退款资金终态触发：存在待开具 → 自动作废；存在已开具 → 自动冲红；并发安全（条件更新先到先得）；
5. 部分退款**不改状态**，仅置"待人工处理"标记（O6）。

#### 15.4.2 抬头管理

- 类型：PERSONAL（个人，抬头=姓名）/ COMPANY（企业，抬头=企业名称，**税号必填**，格式校验规则契约阶段定稿）；
- Phase 1 建议**随批交付常用抬头管理**（`invoice_title`，一用户多抬头、至多一条默认；申请时现填或引用）——取舍见 O2/O3；
- 抬头信息申请时**快照**进发票单（对齐"地址/商品快照"数据约束），抬头变更不影响已申请发票；
- PII 口径见 §15.8。

#### 15.4.3 金额口径与退款联动金额

- 开票金额 = payAmount 快照（细则见 D3）；
- 全额冲红金额 = 原票开票金额；
- 换开重开金额 = payAmount（换开前提是未发生退款）；
- 部分退款后人工冲红再重开的金额 = payAmount − 已退金额（**Phase 2 精确规则**，Phase 1 人工操作留痕于冲红原因/备注）。

#### 15.4.4 触达与催开

- 站内信触达（复用 notification 管道先例，ADR-042：本地事务外 fail-open 发送）：开具成功 / 冲红（自动+人工）/ 作废 → 买家站内信；催开 → 平台管理端侧通知（O10）；
- 催开限频：同发票单 24h 一次（Redis 限频，verification 重发限流同款思路）；
- 时间窗临期（如到期前 7 天仍未开具）管理端列表高亮（Phase 1 不做主动推送）。

### 15.8 非功能性需求

1. **PII 加密与脱敏**：税号/邮箱按三字段模型落库（cipher=AES-256-GCM + hash=HMAC-SHA256 盲索引 + mask=脱敏展示，密钥走 `CryptoKeyConfig`，与 04 §3.1 user 表先例同构）；VO 一律出 mask 值，禁止暴露 cipher/hash/version；日志禁止打印税号/邮箱全量值（09-Constraints 脱敏约束）。手机号 Phase 1 不采集（如启用按同口径三字段）。
2. **审计**：INV7/INV8/INV9/INV10 加 `@OperationLog`（AD51-53 管理端三写先例）；按 ADR-032 双管道口径**注解只写 AUDIT 日志、不落库**；发票域是否扩展 operation_log 显式落库见 O8。
3. **幂等与并发**：申请"先查后插 + `uk_order_active` 兜底"双路径（DuplicateKey → 400，AD51-53 先例）；开具/作废/冲红全部条件更新（0 行=状态冲突）；催开 Redis 24h 限频。
4. **限流**：INV1 加 `@RateLimit`（超限 `FREQUENT_ERROR(429)`）。
5. **模拟开具可替换性（防腐设计方向）**：`domain/port` 定义 `InvoiceIssuePort`（issue/void/redFlush 三操作）+ `infrastructure/adapter` 模拟实现（配置开关如 `invoice.issue.provider=mock`）；Phase 2 税局/电子发票服务商 Adapter 平滑替换，app/domain 零改动（对齐 ai-service 领域端口先例 ADR-039、第三方 SDK 收口 ia-integration 先例）；状态机与红字记录不依赖具体服务商语义。
6. **触达可靠性**：站内信走 notification，本地事务外 fail-open 发送（ADR-042 先例）——触达失败不回滚发票主流程。
7. **越权与下载安全**：买家端资源强校验本人归属；样票 PDF 走 MinIO 签名 URL（头像上传先例），水印"样票"。

### 15.9 分阶段边界

**Phase 1（本 PRD 评审范围，模拟环境）**：

- 电子普通发票（模拟开具 + 简化 PDF 样票）+ 个人/企业抬头 + 常用抬头管理（O2）；
- 一单一票（换开 = 冲红重开）、金额 = payAmount 快照、时间窗 90 天（O1 待裁决）；
- 全额退款自动冲红/作废（资金终态触发）；部分退款人工标记处理（简化口径）；
- 买家：申请/撤回/催开/列表详情/下载；管理端：分页/开具/作废/冲红/导出；
- 站内信触达、管理端审计、PII 三字段、落位 trade-service（O9）。

**Phase 2（roadmap，评审后独立排期）**：

- 真实税局/电子发票服务商对接（防腐 Adapter 替换）、真实票号与版式；
- 增值税专用发票（购方完整要素 + 抵扣）；
- 部分退款按金额精确部分红字（红字信息表口径）；
- 邮件真实交付；商家自助开票工作台（商家端开具——D1 完整形态）；
- 开票失败重试与补偿任务（对齐 `RefundResumeJob` 先例）；一单多票拆分（如需）。

**明确不做**：

- 纸质发票与邮寄；平台自营开票（无自营线，D1）；跨境电商发票、多币种发票（与 AGENTS ⚪ 门禁清单同源）；税务机关代开。

### 15.11 验收标准汇总

| 类别 | 验收项 | 对应 |
| ---- | ------ | ---- |
| 买家申请 | 仅已完成 + 时间窗内可申请；金额 = payAmount 快照（含运费扣优惠）；企业抬头税号必填；一单一票拒绝重复申请 | US-INV-1；§15.5.1 五场景 |
| 抬头 | 抬头 CRUD + 默认一条；快照进发票单；变更不影响已申请发票 | US-INV-2；§15.4.2 |
| 查看下载 | 分页 + 状态筛选 + 脱敏展示；仅"已开具"可下载样票；仅本人可见 | US-INV-3/4；越权场景 |
| 换开撤回 | 换开 = 原票冲红 + 新票待开具且关联原票；撤回仅限待开具；任一时刻至多一张有效票 | US-INV-5/6；§15.5.3 |
| 催开 | 超时 M 天可催开；24h 限频；触达管理端 | US-INV-7；§15.5.3 |
| 退款联动 | 全额退款自动冲红/作废（仅资金终态触发）；重复触发幂等；部分退款标记人工处理不自动红字 | US-INV-8；§15.5.2 五场景 |
| 管理端 | 开具（1→2 模拟票号+样票+审计）；作废守卫（已开具拒绝）；冲红（原因必填+幂等）；导出（脱敏+审计） | US-INV-9~13；§15.5.4 |
| 非功能 | PII 三字段 + VO 脱敏；管理端动作 @OperationLog；条件更新状态机；INV1 限流；开票防腐端口 | §15.8 |
