## 一、产品愿景

**冰美商城 (IcedAmericanoMall)** 是 B2B2C 模式的电商平台，类似淘宝/京东。目标是打造一个集用户购物、商家运营、平台管理于一体的分布式微服务电商系统。

**核心理念**：结合业界主流技术方案与大型互联网公司的工程实践，探索个人全栈开发的最佳路径。不追求空洞的「高可用」「高并发」口号，而是用**技术方案 + 量化结果 + 业务价值**说话。

### 目标特性（量化指标）

| 特性   | 目标                          | 衡量方式                 |
| ---- | --------------------------- | -------------------- |
| 高并发  | 峰值 12000 TPS，P99 延迟 < 500ms | 压力测试报告               |
| 易维护  | 配置变更无需重启，发布频率从周级→日级         | Nacos 配置中心 + 自动化部署   |
| 稳定性  | 电商大促期间零故障                   | 故障记录                 |
| 可扩展性 | 用户量从 10 万→1000 万无需重构        | 架构评审                 |
| 可观测性 | 故障定位从小时级→分钟级                | Prometheus + Grafana |
| 安全性  | 满足等保 2.0 要求                 | 安全审计                 |

## 二、用户角色

| 角色        | 描述                    | 典型行为                       |
| --------- | --------------------- | -------------------------- |
| **游客**    | 未登录用户                 | 浏览商品、搜索、查看商品详情             |
| **普通用户**  | 已注册登录用户               | 下单支付、积分签到、收藏、管理地址          |
| **商家**    | 拥有店铺的用户（一个用户只能成为一个商家） | 管理商品、处理订单、发货、查看数据          |
| **管理员**   | 平台最高权限                | 管理用户/商家/商品/订单、营销配置、数据统计    |
| **第三方系统** | 外部服务                  | 支付网关（微信/支付宝）、短信服务、OSS 对象存储 |

### 登录策略（完整支持，逐步实现）

- 单地登录 / 多地登录 / 多端登录 / 单端登录 / 同端互斥登录
- 七天免登录
- 空闲超时：半小时无操作后需重新登录

### 3.13 买家-商家消息系统（V3.3 ✅）

> **大厂对标**: 淘宝旺旺（独立消息系统 + 店小蜜嵌入）+ 京东咚咚（JIMI客服嵌入IM）。
> 大厂把买家-商家 IM 定位为**独立消息系统**，AI 是嵌入在消息系统中的**辅助能力**（商家离线/繁忙时自动代答）。

#### 消息系统（基础设施）

| 功能 | 阶段 | 说明 |
|------|------|------|
| WebSocket 长连接 | ✅ V3.3 | gateway-service 统一 WebSocket 入口，STOMP 子协议，心跳保活 |
| 买家-商家实时消息 | ✅ V3.3 | 商品详情页/订单列表页发起对话，消息已读/未读状态，conversation_id 会话隔离 |
| 消息持久化 | ✅ V3.3 | `chat_message` 表 MySQL 存储 + Redis 最近 100 条热缓存，分页查询历史 |
| 离线消息推送 | ✅ V3.3 | RabbitMQ 延迟队列 → WebSocket 推送 → App 通知栏 |

#### 店铺 AI（嵌入消息系统）

| 功能 | 阶段 | 说明 |
|------|------|------|
| 商家知识库管理 | ✅ V3.3 | 商家后台上传 FAQ/政策/产品手册 → `merchant_knowledge_base` 表 → ES 索引 |
| 商家 AI 自动代答 | ✅ V3.3 | 仅检索本店知识库（非全平台），复用 `CustomerServiceAssistant` + `RAGRetriever` |
| 商家对话模板 | ✅ V3.3 | `merchant_reply_template` CRUD：欢迎语/离线回复/FAQ 模板/快捷话术 |
| 人机转接通知 | ✅ V3.3 | AI 置信度 < 0.7 → 消息系统内通知商家（非独立工单系统） |

**技术方案**：
- **消息系统**: WebSocket + STOMP + RabbitMQ（与 AI 服务解耦，独立演进）
- **店铺 AI**: 复用 `ai-service` 现有 `CustomerServiceAssistant`，限定检索范围为 `seller_id` 的知识库
- **对话模板**: 商家后台 CRUD → RAG 检索时优先匹配模板 → 模板命中直接返回，不调 LLM（省成本）
- **知识库隔离**: 商家只能管理本店知识库，RAG 检索时过滤 `seller_id`

**技术方案**：
- **详情页数据聚合**: `GET /api/item/product/{id}/detail` 一次返回完整数据（商品+SKU+店铺+评论摘要+优惠券）
- **多维度SKU**: `sku_spec_dimension`(维度名)/`sku_spec_option`(选项值) 表 + `spec_json` 字段
- **原价/到手价**: sku 增加 `original_price`，详情页显示"¥到手价 ~~¥原价~~"
- **立即购买**: `POST /api/trade/order/direct { skuId, quantity, addressId, couponId? }` 跳过购物车
- **关注商家**: `store_follow` 表 + `POST /api/shop/follow/{sellerId}`
- **评论增强**: `media_urls` JSON(图+视频URL) + `GET .../filter?rating=5&hasMedia=true&sort=newest`

```gherkin
  以便在平台购物

    When 用户提交注册请求
    Then 创建用户记录，状态为"正常"
    And 返回 JWT Token 和用户信息
    And 验证码从 Redis 中删除

  Scenario: 重复手机号注册
    Given 手机号 "13800138000" 已被注册
    When 用户提交注册请求
    Then 返回错误 "手机号已注册"

  Scenario: 验证码错误
    Given 手机号 "13800138000" 未被注册
    And 验证码 "123456" 不正确或已过期
    When 用户提交注册请求
    Then 返回错误 "验证码错误或已过期"

  Scenario: 幂等保护
    Given 用户已成功注册

```

## 八、V5.8 增量需求要点（P1：F5 促销引擎 / F6 会员等级）

### F5 店铺满减/满折促销（营销域 + 交易定价中心）

- **需求**：管理端可创建店铺级满减/满折活动；买家下单时自动应用最优活动，优惠与会员折扣、优惠券可叠加（同类型促销不叠加，取减免最大者）。
- **核心场景（BDD）**：
  - Given 店铺有满 300 减 40 活动，When 购物车商品总额 350 下单，Then discountAmount=40、payAmount=310+postFee
  - Given 同时命中满 300 减 40 与满 200 减 30，When 下单，Then 取减免最大者 40（同类型不叠加）
  - Given 满折 8.5 折封顶 100 元、商品总额 400，When 下单，Then 减免 = min(400×15%, 100) = 60 元
  - Given 商品总额低于门槛，When 下单，Then 不应用该活动（合法业务态，不报错）
  - Given marketing 不可用，When 下单，Then 下单失败（fail-closed，促销不静默失效）
- **Phase 2（roadmap）**：C 端商品页促销标签、N 元 N 件、多活动叠加策略、商品级 scope、多券分摊（开放项 O1）。

### F6 会员等级升降级与权益（用户域 + 交易接线）

- **需求**：买家按累计实付金额（成长值）自动升级会员等级（Phase 1 只升不降），等级带来**会员折扣率**（下单计价）与**积分倍率**（下单奖励积分）两项权益。
- **核心场景（BDD）**：
  - Given 累计实付达 5000 元（GOLD 门槛），When 新订单确认收货，Then 等级升为 GOLD，且成长值流水幂等（同订单号仅入账一次）
  - Given GOLD 会员（98 折），When 下单 200 元商品，Then 会员优惠 4 元计入 discountAmount
  - Given GOLD 会员（1.2 倍积分），When 确认收货实付 100 元，Then 奖励积分按 1.2 倍计算
  - Given user-service 不可用，When 下单，Then 下单成功但按无会员折扣计价（fail-open + 告警）
- **Phase 2（roadmap）**：年度降级考核、运费券/专属客服等权益扩展、管理端等级规则编辑、成长值补账任务。

## 九、V5.9 增量需求要点（P2 第一批：F7 商品向量推荐）

### F7 相似商品推荐（复用 T14 向量管道）

- **需求**：商品详情页展示「相似推荐」——基于商品向量化（名称+描述）的 kNN 相似检索，返回在售商品卡片；用户无感知降级（推荐缺失不报错）。
- **核心场景（BDD）**：

  - Given 商品编辑（名称/描述变更），When 保存，Then 向量幂等覆盖写，后续推荐反映新内容
  - Given 商品已下架，When 组装推荐卡，Then 不出现在结果中（item 侧恒过滤在售）
  - Given ES 或 Embedding 未启用，When 访问推荐位/保存商品，Then 推荐返回空列表、摄取静默跳过（0），主流程零影响
  - Given search-service 不可用，When 保存商品/访问推荐位，Then Feign 降级（哨兵 -1/空列表），主流程零影响
- **Phase 2（roadmap）**：「看了又看」（浏览共现统计）、多路召回与排序、推荐位 CTR 埋点、首页推荐流。

- **Phase 2（roadmap）**：管理端任务 CRUD、新手/周期任务类型、任务奖励翻倍活动、删评重评防刷升级。

  - Given 团 1/3，When 用户 B 参团支付成功，Then 团 2/3；用户 B 重复参同团 → 拒绝（uk_team_user）
  - Given 团 2/3，When 用户 C 参团支付成功，Then 团满员置「已成团」，订单走正常发货流程
  - Given 团 2/3 且超过成团时限，When 结团任务扫描，Then 团置「已失败」，A/B 的订单逐单「取消 + 恢复库存 + 全额原路退款」，退款成功买家收站内信
  - Given 团 2/3，When 用户 C 支付成功但团恰好已被填满（竞态），Then C 的参团失败 → 订单自动取消并全额退款
  - Given 活动不在进行中/团不存在/团已满，When 用户下单，Then 400 拒绝（下单不占团位，未支付订单走既有 30 分钟超时取消）
  - Given 同一订单号，When 退款指令重放，Then 幂等返回既有退款单（biz_ref 锚点）
- **Phase 2（roadmap）**：虚拟团/机器人成团、团成功站内信、多件购买、拼团价与券叠加、MQ 事件化、退款失败补偿任务。

### 15.1 背景与目标

**背景**：

1. **合规刚需**：消费者索要购货凭证时经营者必须出具（消费者权益保护相关规定）。C 端"订单完成后索要发票"是电商平台的基础合规能力，当前平台完全缺失（57 张表、240 端点无一涉发票）。
2. **售后联动缺口**：退款资金流已闭环（售后退款 ADR-035/037、拼团结团退款 ADR-049，`refund_order` 三通道原路退回），但"退了钱、票还在"构成虚开风险——发票必须与退款**资金终态**联动冲红/作废。
3. **B 端报销诉求**：企业买家（团队采购）需要抬头+税号的电子普票用于报销，平台无入口即流失 B 端客单。
4. **从未立项**：INV1-INV3 仅存在于 05 §4.15 V5.0 规划占位（⚪ 未实现，已挂账 roadmap），无 PRD、无数据模型、无契约定稿——本节补齐第一段。

**大厂对标**：

| 平台 | 模式 | 对本项目的启示 |
| ---- | ---- | -------------- |
| 淘宝/天猫 | **商家开票**：买家提交申请与抬头 → 商家用开票工具开具 → 买家下载；平台只提供申请/流转/提醒管道 | B2B2C 同构：销售主体=商家 |
| 京东 | 自营=**平台开票**（下单选抬头、完成后自动开具）；POP 入驻商家=商家开票 | 本平台无自营线，平台开票不适用 |
| 拼多多 | 商家开票为主，超时未开可催开 | 催开机制是买家侧标配 |

**目标**（Phase 1，模拟开具环境）：

- G1 买家可对**已完成**订单申请/查看/下载/换开电子普通发票（个人/企业抬头）；
- G2 全额退款资金终态**自动**联动冲红/作废，消除"退钱留票"虚开风险；
- G3 管理端可开具/作废/冲红/导出，形成可审计的发票处理闭环；
- G4 状态机、金额口径、幂等锚点、PII 口径按真实业务建模——Phase 2 接税局时仅替换"开具"防腐适配器，不推翻模型。

#### D1 开票主体：平台统一开票 vs 商家开票

| 选项 | 说明 | 评估 |
| ---- | ---- | ---- |
| A 平台统一开票 | 平台作为销售主体对买家开票，再与商家二次结算（京东自营模式） | ❌ 本平台是纯平台 B2B2C：销售主体=商家（`orders.seller_id`；货款经商家结算域提现，平台不经手货权），平台开票与销售主体不符，税务上不成立 |
| **B 商家开票（推荐）** | 销售主体=商家，发票以商家名义开具；平台提供申请/流转/触达/导出管道（淘宝/天猫/拼多多主流模式） | ✅ 与 B2B2C 定位、既有结算模型一致；大厂对标同构 |
| C 混合（自营平台开 + 入驻商家开） | 双轨并行 | ❌ 平台无自营线，Phase 1 不引入 |

**推荐 B**。补充口径：Phase 1 处于**模拟开具**环境（无税局对接、无法律效力票据），"开具"动作由**平台管理端集中代办**（角色占位，替代商家税务操作）；Phase 2 真实开票时升级为**商家自助开票工作台**（商家端入口），管理端保留兜底/异常处理。即：**开票主体（商家名义）Phase 1 定稿，开票操作者（管理端代办 → 商家自助）分两阶段演进**。

#### D2 票种范围与开票方式

| 选项 | 说明 | 评估 |
| ---- | ---- | ---- |
| **A Phase 1 电子普通发票（模拟开具）+ 个人/企业抬头（推荐）** | 模拟环境跑通全状态机；Phase 2 增值税专用发票 + 税局（电子发票服务商）对接 | ✅ INV1 占位报文 `{orderNo, type: PERSONAL\|COMPANY, ...}` 即普票口径；模拟开票足以验证全部产品逻辑 |
| B Phase 1 直接做专票 | 购方需地址电话/开户行账号等完整要素 | ❌ 专票必须真实税控才具抵扣效力，模拟无意义；要素复杂度放大 Phase 1 交付面 |
| C Phase 1 只做个人抬头 | 砍掉企业抬头 | ❌ 企业抬头是 B 端报销刚需（G1），且占位契约已含 COMPANY |

**推荐 A**。模拟开具 = 本地模拟开票适配器生成**简化 PDF 样票**（水印"样票"、非税务效力）存 MinIO + 生成模拟票号；真实票号/版式 Phase 2 由服务商返回。

#### D3 开票金额口径（必须精确定义）

| 选项 | 口径 | 评估 |
| ---- | ---- | ---- |
| **A 开票金额 = 实付 payAmount（推荐）** | = totalAmount − discountAmount + postFee，**含运费、扣优惠** | ✅ 与 04-Data-Model §3.7 金额不变式 V2 逐字对齐；消费者实际支付多少开多少 |
| B = totalAmount（商品价合计） | 优惠部分也开给消费者 | ❌ 平台/商家承担的优惠未实际收款，虚增税基；且与退款金额（≤ payAmount）对不齐，冲红闭环断裂 |
| C = 商品价不含运费 | 运费另行处理 | ❌ 运费属价外费用应并入开票额；拆两个金额徒增争议与对账成本 |

**推荐 A**，边界细则：

- 运费**计入**（`postFee` 快照；秒杀单 `postFee=0` 天然成立）；
- 优惠（优惠券/促销/会员折扣，`discountAmount`）**不计入**——未实际支付；
- 金额在申请时从 `orders` 快照进 `invoice.amount`，订单后续任何变更不影响已申请发票（快照原则，对齐"地址/商品快照"数据约束）；
- 拼团单（ADR-049）`discountAmount=0`（拼团价直接快照进订单），开票金额 = payAmount 自然成立；
- 售后退款金额既有校验 ≤ payAmount，全额退款金额恰等于开票金额——全额冲红金额对得齐。

#### D4 退款联动（冲红规则）

| 子决策 | 选项 | 推荐 |
| ------ | ---- | ---- |
| 全额退款 | A 自动冲红/作废（已开具 → 自动冲红；待开具 → 自动作废）vs B 管理端人工冲红 | **A 自动**——"退了钱票还在"是虚开合规风险，人工必漏；自动化把风险收敛进资金终态事件 |
| 部分退款 | A 自动按退款金额开部分红字 vs B 人工处理 | **Phase 1 选 B（简化口径，明确写出）**：部分退款**不**自动红字，发票保持"已开具"并置"部分退款待人工处理"标记，管理端筛选后人工冲红/换开；Phase 2 再按退款金额精确部分红字（红字信息表口径） |
| 触发锚点 | 何种事件触发联动 | **仅资金终态**：退款单成功 / 售后单回写 REFUNDED(5)（ADR-035 条件回写口径）/ 拼团结团退款成功（ADR-049，`GB:{orderNo}` 幂等锚点）。审核中/退款处理中**不**触发 |
| 冲红幂等 | 重复触发 | 已冲红的重复触发 = **幂等空操作**（不重复生成红字记录），对齐 I42 条件回写风格 |

**推荐理由（部分退款简化）**：真实部分红字需按金额拆负数票且各税局口径不一，模拟环境收益低；Phase 1 票量可控（新功能灰度期），人工处理成本可接受。**风险已知**：人工依赖存在漏处理可能——管理端列表必须提供"待人工处理"默认筛选视图，Phase 2 闭环。

#### D5 一单多票？

| 选项 | 说明 | 评估 |
| ---- | ---- | ---- |
| **A 一单一票，换开 = 冲红重开（推荐）** | 任一时刻一订单至多一张**有效**发票（待开具/已开具）；改抬头/改类型走"换开"：原票冲红 + 新票生成（关联原票） | ✅ 幂等锚点清晰（唯一约束兜底）；淘宝/京东 C 端主流即一单一票；换开语义完整覆盖改票诉求 |
| B 一单多票 | 按商品行拆分抬头/金额 | ❌ 金额分摊规则复杂（与《多券金额分摊规则》同级别的开放问题），低频诉求不值得 Phase 1 承担 |

**推荐 A**。数据面以 `uk(order_no, active_flag)` 唯一约束实现"一单一有效票"（利用 MySQL 唯一索引多 NULL 特性，同 04 §3.12 `user_auth` 先例）。

#### D6 开票时间窗

| 选项 | 说明 | 评估 |
| ---- | ---- | ---- |
| **A 仅"已完成"可申请 + 完成后 N 天内（推荐，N 默认 90，见 O1）** | 起算点 = `orders.end_time`（确认收货时间，代码已核实：确认收货 3→4 条件更新并落 `end_time`）；逾期入口关闭，管理端仍可补开 | ✅ 未完成订单退款/取消率高，先开后冲浪费；限期收敛长尾虚开敞口 |
| B 支付成功即可申请 | 票随货开 | ❌ 未发货即开票，取消/退款率放大冲红量 |
| C 完成后不限期 | 永久可开 | ❌ 长尾虚开合规敞口不可控 |

**推荐 A**。N=90 天为业界常见默认（京东支持订单完成后长期限补开、淘宝按店铺配置），具体数值列开放问题 O1 由业务裁决。

#### D7 发票能力落位（工程决策，影响产品边界）

| 选项 | 说明 | 评估 |
| ---- | ---- | ---- |
| **A 落 trade-service（推荐）** | 订单/售后/退款联动同域：金额快照读 `orders`、退款终态事件就近触发冲红，无跨服务回写 | ✅ 联动是本功能的核心复杂度，就近消灭分布式一致性成本 |

### 15.4 功能需求与状态机

#### 15.4.1 发票单状态机

状态定义（`InvoiceStatusEnum`，终态 2 个）：

| 状态 | 值 | 进入方式 | 允许的迁出 |
| ---- | - | -------- | ---------- |
| 待开具 PENDING_ISSUE | 1 | 买家申请成功 | → 已开具（开具）；→ 已作废（买家撤回 / 全额退款守卫自动作废 / 管理端作废） |
| 已开具 ISSUED | 2 | 开具成功（模拟，管理端触发） | → 已冲红（全额退款自动 / 管理端冲红 / 换开前置） |
| 已冲红 RED_FLUSHED | 3 | 冲红成功（生成红字记录） | 终态 |
| 已作废 VOIDED | 4 | 作废成功 | 终态 |

迁移语义（条件更新口径，契约阶段按 05 §九 状态机表格同款定稿）：

| 迁移边 | 触发方 | 条件更新语义（0 行 = 状态冲突） |
| ------ | ------ | ------------------------------ |
| 1→2 开具 | 管理端 | `UPDATE invoice SET status=2, issue_time=?, mock_invoice_no=? WHERE invoice_no=? AND status=1` |
| 1→4 作废 | 买家撤回 / 全额退款守卫 / 管理端 | `AND status=1`；撤回与退款守卫并发时先到先得，后到 0 行按幂等收敛 |
| 2→3 冲红 | 全额退款自动 / 管理端 / 换开前置 | `AND status=2`；已冲红的重复触发 = 幂等空操作 |

**守卫清单**：

1. **已开具不可作废**——只能冲红（防"作废已开票"的合规漏洞）；
2. 已冲红/已作废为终态——不可再开具、不可再冲红（重复触发幂等空操作）；
3. 换开仅对"已开具"有效；原票冲红（2→3）与新票创建（1）在**同一本地事务**（trade 同库，无跨服务）；
4. 全额退款资金终态触发：存在待开具 → 自动作废；存在已开具 → 自动冲红；并发安全（条件更新先到先得）；
5. 部分退款**不改状态**，仅置"待人工处理"标记（O6）。

#### 15.4.2 抬头管理

- 类型：PERSONAL（个人，抬头=姓名）/ COMPANY（企业，抬头=企业名称，**税号必填**，格式校验规则契约阶段定稿）；
- Phase 1 建议**随批交付常用抬头管理**（`invoice_title`，一用户多抬头、至多一条默认；申请时现填或引用）——取舍见 O2/O3；
- 抬头信息申请时**快照**进发票单（对齐"地址/商品快照"数据约束），抬头变更不影响已申请发票；
- PII 口径见 §15.8。

#### 15.4.3 金额口径与退款联动金额

- 开票金额 = payAmount 快照（细则见 D3）；
- 全额冲红金额 = 原票开票金额；
- 换开重开金额 = payAmount（换开前提是未发生退款）；
- 部分退款后人工冲红再重开的金额 = payAmount − 已退金额（**Phase 2 精确规则**，Phase 1 人工操作留痕于冲红原因/备注）。

#### 15.4.4 触达与催开

- 站内信触达（复用 notification 管道先例，ADR-042：本地事务外 fail-open 发送）：开具成功 / 冲红（自动+人工）/ 作废 → 买家站内信；催开 → 平台管理端侧通知（O10）；
- 催开限频：同发票单 24h 一次（Redis 限频，verification 重发限流同款思路）；
- 时间窗临期（如到期前 7 天仍未开具）管理端列表高亮（Phase 1 不做主动推送）。

### 15.8 非功能性需求

1. **PII 加密与脱敏**：税号/邮箱按三字段模型落库（cipher=AES-256-GCM + hash=HMAC-SHA256 盲索引 + mask=脱敏展示，密钥走 `CryptoKeyConfig`，与 04 §3.1 user 表先例同构）；VO 一律出 mask 值，禁止暴露 cipher/hash/version；日志禁止打印税号/邮箱全量值（09-Constraints 脱敏约束）。手机号 Phase 1 不采集（如启用按同口径三字段）。
2. **审计**：INV7/INV8/INV9/INV10 加 `@OperationLog`（AD51-53 管理端三写先例）；按 ADR-032 双管道口径**注解只写 AUDIT 日志、不落库**；发票域是否扩展 operation_log 显式落库见 O8。
3. **幂等与并发**：申请"先查后插 + `uk_order_active` 兜底"双路径（DuplicateKey → 400，AD51-53 先例）；开具/作废/冲红全部条件更新（0 行=状态冲突）；催开 Redis 24h 限频。
4. **限流**：INV1 加 `@RateLimit`（超限 `FREQUENT_ERROR(429)`）。
5. **模拟开具可替换性（防腐设计方向）**：`domain/port` 定义 `InvoiceIssuePort`（issue/void/redFlush 三操作）+ `infrastructure/adapter` 模拟实现（配置开关如 `invoice.issue.provider=mock`）；Phase 2 税局/电子发票服务商 Adapter 平滑替换，app/domain 零改动（对齐 ai-service 领域端口先例 ADR-039、第三方 SDK 收口 ia-integration 先例）；状态机与红字记录不依赖具体服务商语义。
6. **触达可靠性**：站内信走 notification，本地事务外 fail-open 发送（ADR-042 先例）——触达失败不回滚发票主流程。
7. **越权与下载安全**：买家端资源强校验本人归属；样票 PDF 走 MinIO 签名 URL（头像上传先例），水印"样票"。

### 15.9 分阶段边界

**Phase 1（本 PRD 评审范围，模拟环境）**：

- 电子普通发票（模拟开具 + 简化 PDF 样票）+ 个人/企业抬头 + 常用抬头管理（O2）；
- 一单一票（换开 = 冲红重开）、金额 = payAmount 快照、时间窗 90 天（O1 待裁决）；
- 全额退款自动冲红/作废（资金终态触发）；部分退款人工标记处理（简化口径）；
- 买家：申请/撤回/催开/列表详情/下载；管理端：分页/开具/作废/冲红/导出；
- 站内信触达、管理端审计、PII 三字段、落位 trade-service（O9）。

**Phase 2（roadmap，评审后独立排期）**：

- 真实税局/电子发票服务商对接（防腐 Adapter 替换）、真实票号与版式；
- 增值税专用发票（购方完整要素 + 抵扣）；
- 部分退款按金额精确部分红字（红字信息表口径）；
- 邮件真实交付；商家自助开票工作台（商家端开具——D1 完整形态）；
- 开票失败重试与补偿任务（对齐 `RefundResumeJob` 先例）；一单多票拆分（如需）。

**明确不做**：

- 纸质发票与邮寄；平台自营开票（无自营线，D1）；跨境电商发票、多币种发票（与 AGENTS ⚪ 门禁清单同源；多币种整体口径见 §十七——D6 裁决发票恒 CNY）；税务机关代开。

### 16.1 背景与目标

**背景**：

1. **RAG 已交付，但向量检索有明确能力边界**：T14 向量链路（`ai.rag.enabled` 渐进启用 + 全链路 fail-open，02-Architecture §3.4）与同一管道的三次复用（商家知识库 → 商品向量推荐 P27（ADR-046）→ 笔记相似 P34（ADR-048））已验证「分块 + Embedding + ES kNN」模式成熟。但向量检索强在**模糊语义**（同义改写、口语化表达），弱在**精确关系与多跳推理**——"A 品牌的售后政策是什么"这类问题需要「品牌 → 品牌政策条目 → 具体条款」的精确关系链，向量只能召回文本相似的 chunk，无法保证关系链正确，答案易张冠李戴或漏引。13-AI-Technology-Selection §10.1 已把「RAG 关系查询召回率 < 80%」列为知识图谱启动触发器。
2. **知识图谱从未立项**：PRD §3.12 仅 4 行占位（⚪ V3.x 前瞻）；05 契约无任何 KG 端点；docker-compose 无图数据库（现基建：MySQL/Redis/ES/RocketMQ/MinIO/可观测栈，已核实镜像清单）；13 §10.1 触发条件（SKU > 10 万 / 关系类查询占比 > 20% AI 流量 / 关系召回 < 80% / 语义搜索差评率 > 5%）**截至 2026.07 记录均未满足**——13 的结论是"延期至 V3.x"。本 PRD 承接该结论，并给出**不赌触发器的最小成本预研路线**（Phase 1，见 §16.9）：先用结构化直建把图管道建起来，触发器成熟后 Phase 2 叠加抽取型知识。
3. **向量管道已三次复用，图管道可沿用同一节奏**：search-service 已是 ES 域唯一所有者（三个向量索引 `products` / `knowledge_vectors` / `notes`），「I 端点幂等摄取 + kNN/terms 检索 + fail-open 降级定类」模式可原样复制到图边索引——图能力的边际成本主要在**知识构建**而非**基建**。
4. **大厂对标与场景取舍**（电商 KG 四类典型用途）：

| 大厂实践 | 典型用途 | 对本项目的启示 | 取舍 |
| ---- | ---- | ---- | ---- |
| 淘宝/天猫（搭配购、"看了又看"） | 商品关系导购 | 导购是电商确定性收益场景；类目/品牌/商家数据现成 | **✅ Phase 1 聚焦**（§16.2） |
| 京东（店小蜜政策问答） | 政策合规问答（RAG 弱点直接补位） | 依赖知识抽取与治理成熟度 | Phase 2 首位（触发器见 §16.9） |
| 淘宝/京东搜索 | 搜索意图精确化（品牌+类目+属性约束） | SE1 过滤（brand/minPrice/maxPrice/sort，V5.10）+ SE6 facets 已覆盖主诉求 | ❌ 不做（与既有能力重叠，边际收益小） |
| 各大厂风控部门 | 反欺诈/风控图（关联账户/设备识别） | 需要风控域基建与业务闭环 | ❌ 不做（本平台无风控域，非当前痛点） |

**向量 vs 图的能力边界（KG 是"补"不是"替"）**：

| 维度 | 向量检索（已交付） | 知识图谱（本 PRD） |
| ---- | ---- | ---- |
| 擅长 | 模糊语义、同义改写、"类似这个" | 精确关系、多跳推理、可解释引用 |
| 不擅长 | 精确关系链（品牌→政策→条款）、搭配/适配推理 | 模糊语义召回 |
| 失效形态 | 召回错 chunk（静默错误，难察觉） | 关系缺失（空结果，可降级可观测） |
| 数据前提 | 有文本即可 | 需结构化知识（直建/抽取/人工配置） |

**目标**（Phase 1，聚焦场景见 §16.2）：

- G1 商品详情页提供「搭配推荐」卡（图关系召回为主 + 向量相似兜底），"买手机→贴膜+壳+充电器"导购体验落地（兑现 §3.12 占位第 2 行"场景化搭配推荐"）；
- G2 图管道（存储 + 摄取 + 查询 + 最小治理）按最小成本建立，与既有向量管道同域同模式，Phase 2 场景（政策问答 / 可视化后台）可平滑叠加而不推翻管道；
- G3 全链路 fail-open 纪律落地：KG 任一环节失效**绝不阻断**商品详情/客服应答（对齐 RAG fail-open 与 ADR-011 降级三分法）；
- G4 最小治理面交付：类目搭配规则 CRUD + 关系查询 + 审计，运营可自助维护导购知识。

| 查询形态 | ★ 原生多跳/最短路径/图算法 | 🟡 ≤2 跳（terms 两次往返）可控；≥3 跳往返指数膨胀、无图算法 | 🔴 多跳靠自连接，弱查询面、无检索能力 | 🟡 检索面同 B；真相面可审计可修复 |
| 与现有 RAG 管道整合成本 | 🔴 向量/图两套引擎两套链路，fail-open 纪律需重立 | 🟢 与向量同域同模式（I 端点 + 索引 + fail-open 先例） | 🟡 检索面另建 | 🟢 检索面同 B + 治理写面自然（04 数据模型约定） |

**推荐：Phase 1 = D 混合的最小形态**，并诚实说明其在 Phase 1 的真实构成（"混合"在此并非两套存储各存一份全量图）：

1. **直建关系不新增任何 MySQL 存储**——BELONGS_TO（`product.category_id`）、PARENT_OF（`category.parent_id`）、SOLD_BY（`product.seller_id`）的真相就是源表列；BRAND_OF 的真相是 `product.brand` 字符串（规范化后作值节点，是否实体化见 O4）；
2. **人工知识唯一新增表**：`pairing_rule`（类目搭配规则，治理/审计/软删按 04-Data-Model 约定）；
3. **ES 检索面新增 `kg_edges` 边文档索引**（对齐 products/notes 索引模式），查询 = terms 组合（≤2 跳 = 两次往返，Phase 1 明示能力边界）；
4. **演进路线**：Phase 2 引入 LLM 抽取后，抽取关系落 MySQL 邻接表 `kg_relation`（source/status/confidence 三治理字段——审核队列的真相面），ES 投影同步；**NebulaGraph 仅当 §16.9 量化触发器满足**（≥2 项）时立项评审，替换面收敛在图查询端口（`GraphQueryPort`，对齐 §15.8.5 `InvoiceIssuePort` 防腐先例与 ai-service 领域端口先例 ADR-039），app/domain 零改动。13 §10.2「NebulaGraph 首选」结论**保留但前提化**——其成立前提（SKU > 10 万等触发条件）当前未满足，且 13 §10.1 自身结论即为"当前判断：条件均未达到，延期"。

**B 纯 ES 方案落选理由**（评审关注）：边文档只存 ES 则治理写面（规则启停/审计/软删）缺乏关系型真相，与 04「真相源 MySQL、ES 为投影」的既定约定相悖；且规则数据无论如何都需要 MySQL 存储——纯 ES 并不省掉任何东西，只是丢掉真相面。

**C 纯 MySQL 方案落选理由**：直建关系确实无需邻接表（见上），但 Phase 1 的检索面（按关系类型批量取邻居、与向量结果融合）在 MySQL 自连接形态下查询能力弱、且与 search-service ES 域所有权先例（02 §3.4）不接续；Phase 2 抽取边量上来后自连接成本失控。

**引入 NebulaGraph 的真实成本（写透，不以"前瞻"两字带过）**：新增 3 角色容器编排与资源配额（生产建议 storaged ≥3 副本）；nGQL 学习曲线与团队 Java/ES/MySQL 栈零重叠，单人项目等于单点知识；Prometheus exporter / 日志 / 备份恢复均需从零接入现有可观测栈；与向量链路形成双引擎双 fail-open 语义，降级矩阵翻倍。Phase 1 边量（万级）远未达到其收益拐点——**"不引入新图库"是本 PRD 的默认态**。

#### D2 知识来源与构建方式

| 选项 | 说明 | 评估 |
| ---- | ---- | ---- |
| **A 结构化数据直建（Phase 1 采用）** | 表级关系从源表列直建（product/category/seller）；搭配关系由运营类目级规则配置 | ✅ 零抽取成本、可信度 100%（来源即业务主数据）、可回滚可重建（reindex 兜底） |
| B LLM 从文本抽取 | 售后政策/商品描述/种草笔记 → 实体识别 + 关系抽取 | 🔴 可信度 < 100%（幻觉/漏抽/错抽），必须配置信度阈值 + 人工审核队列 + 实体对齐——治理成本是抽取本身数倍；政策文本当前为自由文本，无结构化兜底 |
| C 混合 | A 为主 + B 试点 | ✅ 推荐的**分期形态**：Phase 1 = A（②场景天然直建）；Phase 2 = C（①场景引入 B，带 §16.8 置信度治理） |

**推荐 C 的分期形态（Phase 1 = A）**。补充口径：Phase 1 的"适配/配件"关系**不靠 LLM**——用类目级搭配规则（运营配置"手机 → 贴膜/保护壳/充电器类目"）覆盖，规则是人类可读、可审计、可启停的，从根上规避抽取可信度问题；商品级 requires/compatible_with（"该型号专用壳"）留 Phase 2 抽取（带审核）。

#### D3 知识更新机制

| 选项 | 说明 | 评估 |
| ---- | ---- | ---- |
| **A 变更事件同步（afterCommit 旁路，推荐主路径）** | 商品/类目/规则变更 → afterCommit 增量摄取边 | ✅ 实时性好；先例成熟（P27 摄取钩子、ADR-047/048）；失败仅 WARN 不回滚主事务 |
| B 定时全量重建 | XXL-Job 周期 reindex | 🟡 延迟 T+1、全量成本随边量线性涨；但作为兜底不可少 |
| C 人工维护 | 治理端 CRUD 即时写 | ✅ 对人工知识（规则）天然成立 |

**推荐 A + C 为主、B 兜底（三轨并行，各自覆盖其真相源）**：源数据变更走 A（商品/类目编辑后 afterCommit 摄取）；规则治理走 C（CRUD 即时写真相并同步投影）；A 失败/漏摄取与存量回填走 B（图索引全量重建，对齐 search reindex 先例与 ADR-046 的 reindex 修复）。

#### D4 检索融合策略

| 选项 | 形态 | 评估 |
| ---- | ---- | ---- |
| A KG 先行约束 + 向量召回 | query → KG 精确定位实体/关系 → 以实体约束向量检索上下文 | ✅ 问答场景最优（Phase 2 ①）；Phase 1 导购无 query 侧，不适用 |
| **B 双路召回 + 融合重排** | 向量一路 + 图一路，RRF/加权融合 | ✅ 通用；对齐 13 §5.3 混合检索框架的"结构化路径"占位 |
| C KG 仅做答案解释与引用 | 向量照旧，KG 附关系依据 | 🔴 投入产出比最低（建了图只当引用脚注），不采纳 |

**推荐：Phase 1（导购）取 B 的实体驱动变体**——图召回为主路径（商品 → KG 邻居 → 候选商品集），既有向量相似（P27 管道）作排序信号与空关系兜底——"向量管相似、图管相关"，两卡共存（位次见 O6）；**Phase 2（问答）取 A**——新增 `KgContextRetriever` 与既有 `RAGRetriever` 并列注入应答上下文（各自独立 fail-open，互不拖拽，形态对齐 02 §3.4 检索链路）。

### 16.4 图模型草案（草案——规格先行阶段定稿）

> 按 Phase 1 场景 ②（商品关系导购）裁剪；Phase 2 实体以"（P2）"标注。存储落位对齐 D1 推荐方案。

**实体（节点）**：

| 实体 | 真相源 | 节点标识 | 阶段 |
| ---- | ---- | ---- | ---- |
| 商品 Product | `product` 表 | product.id（技术主键；对外展示用 `product_id` 业务键） | P1 |
| 类目 Category | `category` 表 | category.id | P1 |
| 品牌 Brand | `product.brand` 字符串（规范化，同名字符串归并为同一品牌节点） | brand_key（规范化名称）——**值节点，无物理表**（是否新建 brand 表见 O4） | P1 |
| 店铺/商家 Seller | `seller` / `shop` 表 | seller.id | P1 |
| 政策条目 PolicyEntry | LLM 抽取自平台政策/商家知识库文本 | policy_entry_id | （P2） |
| 笔记/属性/场景实体 | `note` / `product.attributes`（JSON K-V） | — | （P2） |

**关系（边）**：

| 关系 | 方向 | 来源 | 构建方式 | 属性 | 阶段 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| BELONGS_TO 属于类目 | product → category | `product.category_id` | 直建 | source=DIRECT | P1 |
| PARENT_OF 类目层级 | category → category | `category.parent_id` | 直建 | source=DIRECT | P1 |
| BRAND_OF 品牌 | product → brand | `product.brand`（规范化） | 直建 | source=DIRECT | P1 |
| SOLD_BY 销售 | product → seller | `product.seller_id` | 直建 | source=DIRECT | P1 |
| PAIR_WITH 搭配 | category ↔ category | 运营规则（`pairing_rule`） | 人工配置 | weight（排序权重）、source=RULE、status（1 启用/0 停用） | P1 |
| REQUIRES / COMPATIBLE_WITH 配件适配 | product → product | 商品描述/参数 | LLM 抽取 + 审核 | confidence、reviewStatus | （P2） |
| SUBSTITUTE_OF 替代 | product → product | 描述/评价 | LLM 抽取 + 审核 | confidence | （P2） |
| EXPLAINS 政策解释 | policyEntry → brand/category | 政策文本 | LLM 抽取 + 审核 | confidence | （P2） |

**与现有表/索引的映射关系**：

| 图元素 | 真相源（MySQL） | 检索面（ES） | 说明 |
| ---- | ---- | ---- | ---- |
| BELONGS_TO / PARENT_OF / BRAND_OF / SOLD_BY 边 | 源表列（零新增存储） | `kg_edges` 边文档索引 | 摄取时物化为边文档 |
| PAIR_WITH 边 | `pairing_rule` 表（**Phase 1 唯一新增表**） | `kg_edges` | 治理写真相，同步投影 |
| （P2）EXTRACTED 边 | `kg_relation` 邻接表（P2 新增：source/status/confidence） | `kg_edges` | 审核队列真相面 |
| 向量（对照，不变） | — | `products` / `knowledge_vectors` / `notes` | 既有三索引，本 PRD 零改动 |

`kg_edges` 边文档结构草案：

```json
{
  "edgeId": "product:1001:BELONGS_TO:category:10",
  "srcType": "product", "srcId": "1001",
  "relType": "BELONGS_TO", "dstType": "category", "dstId": "10",
  "weight": 0, "source": "DIRECT", "status": 1,
  "updateTime": 1728000000000
}
```

**查询形态与能力边界（Phase 1 明示）**：仅承诺 ≤2 跳——典型链路"商品 P1 →(BELONGS_TO) 类目 C10 →(PAIR_WITH) 类目 C20 → 类目 C20 在售商品"为两次 terms 往返；≥3 跳不做（成本指数增长，NebulaGraph 触发器 (b) 监控项）。

#### 16.6.1 知识构建（直建与规则）

```gherkin
Feature: 图知识构建
  作为平台
  我希望商品关系以直建与规则两种方式进入图管道
  以保证知识可信且可治理

  Scenario: 商品发布触发直建边摄取
    Given 商家发布商品 P1（类目"手机" C10、品牌"冰美"、店铺 S1）
    When 商品保存事务提交
    Then afterCommit 旁路摄取直建边（P1→C10 BELONGS_TO、P1→BRAND:冰美 BRAND_OF、P1→S1 SOLD_BY）
    And 摄取失败仅记 WARN，商品保存主流程零影响

  Scenario: 同商品重复摄取幂等覆盖写
    Given 商品 P1 已摄取过直建边（BELONGS_TO → C10）
    When 商品编辑（改类目为 C11）再次触发摄取
    Then P1 的边按 src 先删后写幂等覆盖（BELONGS_TO 更新为 P1→C11，不产生重复边）

  Scenario: 类目搭配规则配置即时生效
    Given 类目 C10（手机）与 C20（手机配件）均存在

    Then 规则落库（唯一约束防重）并同步边投影

  Scenario: 规则停用后邻居查询不再返回
    Given 搭配规则 C10→C20 已存在且启用
```


### 16.8 非功能性需求

1. **降级纪律（最高优先级）**：KG 是**纯旁路增强能力**，全链路 fail-open——摄取失败仅 WARN、查询失败返回空/兜底、边投影同步失败不阻断规则落库；**KG 失效绝不阻断商品详情与客服应答主流程**（对齐 ADR-046 降级定类「推荐纯旁路全链路 fail-open，与 I43/I44 fail-closed 刻意不同」、ADR-011 三分法「展示型查询返回空值」、02 §3.4 RAG fail-open 同款）。若未来 KG 结果进入判别/命令场景（计价/履约决策），必须显式 fail-closed 并单独评审——Phase 1 无此类场景。
2. **抽取置信度治理（Phase 2 生效，Phase 1 验收预留）**：confidence ≥ 0.80 自动 ACTIVE；0.50–0.79 进人工审核队列（PENDING，不参与检索）；< 0.50 丢弃。审核队列积压 > 7 天告警；双阈值可配置（O8）。
3. **性能预算**：I58 邻居查询（≤2 跳 = terms 两次往返）P95 < 200ms；P35 搭配卡端到端 P95 < 500ms（含 Feign 与组装）；摄取走 afterCommit 异步，不占商品保存主流程耗时。
4. **幂等与一致性**：I57 按 src 先删后写幂等（对齐 I37/I47）；规则编辑 null-safe + 唯一约束兜底（DuplicateKey 回落 400，AD51-53 先例）；增量摄取与全量重建并发安全（按 src 先删后写自然收敛）。
5. **审计**：AD61-63 全部 `@OperationLog`（ADR-032 管道一，单行 JSON → logger AUDIT，注解只写日志不落库）；图索引重建操作同样审计。
6. **越权与数据边界**：治理面仅管理端 🔑（`@PreAuthorize` 管理端先例）；Phase 1 搭配规则为**平台级类目规则**，不开放商家级（商家间公平性问题，留 Phase 2 与 O7 一并裁决）；P35 为公开 GET，响应不含 version/cipher/hash 技术字段（09-Constraints VO 约束）。

### 16.9 分阶段边界

**Phase 1（本 PRD 评审范围）**：

- 场景 ② 商品关系导购：直建边（BELONGS_TO / PARENT_OF / BRAND_OF / SOLD_BY）+ 类目搭配规则（PAIR_WITH）；

**Phase 2（roadmap，评审后独立排期；分场景触发器）**：

- **场景 ① 客服政策问答 KG 化**——启动触发器沿 13 §10.1（任一满足即评估立项）：SKU > 10 万 / 关系类查询占比 > 20% AI 流量 / RAG 关系查询召回 < 80% / 语义搜索差评率 > 5%。交付面：LLM 抽取（D2-B）+ 实体对齐 + 审核队列（D6-B）+ `KgContextRetriever`（D4-A）；

  未满足前 13 §10.2「NebulaGraph 首选」结论保留但不执行；
- 商品级适配关系（requires/compatible_with）、品牌实体表（O4）、商家级搭配规则（O7）、图数据健康度大盘。

### 17.1 背景与目标

**动机矩阵**（三档动机的价值与合规成本完全不对称——这决定了分阶段边界）：

| # | 动机 | 价值 | 工程成本 | 合规成本 | 判断 |
| - | ---- | ---- | ---- | ---- | ---- |
| M1 | 海外买家展示本币价格 | 转化率（消除价格心理门槛）；站内体验国际化 | **低**——展示层换算，交易链路零侵入 | **低**——展示免责即可，不涉及收汇 | **✅ Phase 1 兑现** |
| M2 | 跨境商家入驻 | 供给扩容（海外商品/品牌） | 高——商家外币定价、CNY 折算入账、结算口径 | 高——跨境贸易资质、海关/检疫 | ❌ Phase 1 不做（触发器化 §17.8） |
| M3 | 多币种收款与结算 | 海外买家支付成功率（本币支付） | **极高**——支付渠道/对账/退款/钱包/结算全链路重构 | **极高**——跨境收单资质、外汇申报、税基口径 | ❌ Phase 1 不做（立项条件清单 §17.8） |

> 诚实评估：本平台当前**无任何海外流量证据**（国内 B2B2C，类淘宝/京东）。M1 的真实价值依赖海外买家占比数据（Phase 2 触发器 (a) 的监控项），Phase 1 的定位是**低成本能力预置**——用最小代价把「展示换算」建起来并验证数据，而非赌海外需求。

**大厂对标**：

| 平台 | 模式 | 对本项目的启示 |
| ---- | ---- | -------------- |
| Amazon | 多币种展示 + **本币结算**（Currency Converter：下单时锁定汇率并明示换汇手续费缓冲） | 展示换算与结算换算是两层能力；下单时点锁汇率是订单详情一致性的行业做法 |
| Shein / Temu | **全本地化定价**（定价即本币，非换算；独立站点 + 独立法人 + 本地支付） | 「多币种结算」的真实形态是站点级/法人级投入，不是在既有单体上加字段——反证 Phase 1 不应碰结算 |
| 京东国际 | 跨境专区，**人民币计价为主** + 关税/税费明细展示 | 国内平台跨境线仍以 CNY 结算为锚；展示层国际化的最小可用形态 |

**目标**（Phase 1）：

- G1 海外买家可切换展示币种，商品列表/详情/搜索卡/购物车/订单确认页以「CNY 主价 + 本币参考价」双价展示；
- G2 下单时点锁定展示汇率快照（若 D1 采纳折中案），订单详情按快照汇率展示参考价，历史一致可审计；
- G3 换算**零侵入**：不改任何既有金额字段语义、不引入 BigDecimal/浮点、支付/退款/钱包/对账/发票/结算链路 CNY 分原样；
- G4 管理端可配置币种与汇率（启用清单/汇率修正/生效时间），汇率服务失效自动降级回 CNY 展示。

#### D1 范围定界（本 PRD 最重决策）：纯展示 vs 折中 vs 全链路结算

| 维度 | A 全链路多币种结算 | **B 折中：展示换算 + 订单快照锁汇率（推荐）** | C 纯展示换算（零 schema 改动） |
| ---- | ---- | ---- | ---- |

**推荐 B**。理由：

1. **C 的唯一硬伤是订单详情参考价漂移**——用户下单时看到 ≈$19.08，三天后回看变成 ≈$19.15，纯展示链路解释成本高于两列 schema 成本；大厂做法均为下单时点锁定（Amazon Currency Converter 下单锁汇并展示）；
2. **B 的 schema 代价可控且有界**：两列均可空（NULL = CNY 订单/快照降级），不参与金额不变式，列名以 `display_*` 前缀显式标注「展示参考快照，非结算币种」，防止后续开发者误读为结算币种（该风险写入 04 定稿时的列注释与 §17.7 NFR）；
3. **A 不是 Phase 1 选项**：其成立前提（跨境收单资质、财税口径、渠道改造）全部不具备，条件清单如下——

**「多币种结算」立项条件清单**（Phase 2 触发器，量化见 §17.8）：

- 合规硬性：跨境收单资质签约（微信支付跨境商户 / 支付宝国际 / Stripe / PayPal 至少一家）；
- 财税硬性：外汇收入申报与税基口径方案获财务/税务确认（含汇差损益归属规则）；

- 技术评审：支付渠道按币种扩展、对账币种维度、退款原路退回汇差处理、锁汇时点（下单 vs 支付）四项方案过架构评审。

#### D4 换算精度与舍入（金额纪律红线的技术落点）

**问题**：汇率天然是小数（1 CNY ≈ 0.1403 USD ≈ 20.91 JPY），而 09-Constraints 硬约束「金额禁 `float/double/BigDecimal`」。**解法：定点整数（fixed-point integer）**——与「金额 = INT 分」同构思想，把小数放大成整数存算，全程整数乘除：

- **汇率存储**：`rate_scaled` BIGINT = 「每 1 元人民币兑换目标币**主单位**数 × 10⁶」（固定 10⁻⁶ 主单位刻度）。例：USD 0.140300 → `140300`；JPY 20.910000 → `20910000`；KRW 190.000000 → `190000000`。用 BIGINT 而非 INT 是为兜底高比率币种（如 IDR 1 CNY ≈ 2200）不溢出——汇率是**换算参数不是金额**，不受「金额 INT 分」字段类型约束，但同样**严禁浮点**；
- **换算公式（纯整数）**：目标币最小单位数 = `round(amountCNY × rate_scaled × 10^exponent ÷ 10⁸)`（half-up 四舍五入）。`exponent` 为目标币种 ISO 4217 最小单位指数（USD/EUR/CNY=2、JPY/KRW=0、BHD/KWD=3），存于币种表；
- **算例**（BDD 同款）：① USD：商品 12800 分 × 0.1403 = 17.9584 USD → 1796 美分 = **$17.96**；② **日元无分案例**：10 元（1000 分）× 20.91 = 209.1 円，JPY 最小单位 = 1 円 → **209 円**（无小数位）；③ 韩元同 JPY（exponent=0）；
- **舍入规则**：half-up 四舍五入到目标币种最小单位，**方向全平台统一**（不引入「向上取整避险」——Phase 1 支付恒 CNY，无支付差异可避险；Phase 2 若做结算再按换汇成本裁决方向）；
- **行/总额一致性**：整单参考价以 **CNY 整单总额为换算基准**（`payAmount` 口径），行金额各自换算仅作行级参考——两者可能相差 ±1 最小单位，展示以总额口径为准（禁止「行价求和当总额」，消除累加舍入漂移）；
- **换算仅展示**：换算结果不落业务表（快照列存的是**汇率**而非换算后金额）、不参与任何金额不变式、不进任何 Feign DTO 金额字段。

#### D5 支付渠道

| 阶段 | 口径 |
| ---- | ---- |
| **Phase 1（推荐采纳）** | **支付零改动**：WECHAT（Pay v3 CNY）/ ALIPAY（Mock）/ BALANCE（钱包 CNY）三通道原样；支付单 `pay_order.amount` 恒 CNY 分；支付页金额恒 CNY + 免责声明常驻（D6）；买家展示币种不影响任何支付报文 |

#### D6 税务/合规/发票

- **发票恒 CNY**：`invoice.amount` = `payAmount` 快照（CNY 分，§十五 D3 已定稿口径）**零改动**；「跨境电商发票、多币种发票」在 §十五.9 已列为明确不做，本 PRD 维持——Phase 2 多币种结算落地时发票仍以 CNY 税基开具（外币收入折算口径由财税方案定义）；
- **展示免责声明**：所有本币参考价旁常驻固定文案——**「汇率仅供参考，实际支付金额以人民币（CNY）为准」**；措辞属前端 UI 层责任，落位 `16-Frontend-Product-Design` 定稿（O10 法务审校），API 不承载免责文案（前端静态常量）；
- **展示价不构成计价依据**：本币参考价不进入订单契约语义（订单金额四字段恒 CNY 分），客服/争议处理一律以 CNY 金额为准；
- **合规成本声明**：Phase 1 不涉及跨境收单、外汇申报、海关与税务——这是 D1 推荐 B/C 而非 A 的根本原因之一。

#### D7 落位（工程决策，影响产品边界）

**前置子决策——换算执行点：后端换算 vs 前端换算**

| 选项 | 说明 | 评估 |
| ---- | ---- | ---- |
| **A 前端换算（推荐）** | 后端 API 恒返回 CNY 分（**契约零改动**）；前端经「币种列表+汇率」端点取数后本地换算展示 | ✅ P1/P2/M/T 系全部展示端点 VO 零改动（后端换算需每端点加 `targetCurrency` 参数 + VO 增字段，契约面爆炸）；换算零后端开销；规则确定性由共享测试向量保证（NFR §17.7.3） |
| B 后端换算 | 服务端按请求币种换算后返回 | ❌ 契约面侵入全仓展示端点；与「契约零改动」目标冲突；仅 Phase 2 结算场景才需要服务端换算 |

**落位主决策——币种/汇率数据归属**：

| 选项 | 说明 | 评估 |
| ---- | ---- | ---- |
| A marketing-service | 营销域承载「价格呈现」 | ❌ 汇率不进入任何成交价（`discountAmount` 是促销的产物），归属牵强 |
| B trade-service | 快照消费方就近，零 Feign | ❌ trade 已是最重服务（Saga/Sentinel/10 controllers 豁免态），塞平台级配置数据职责不符；C 端汇率查询挂 `/api/trade/**` 语义差 |
| C 新建 currency-service | 独立轻量域 | ❌ 单能力新增服务（Feign/网关/部署面膨胀），§15.2 D7-B（invoice-service）同款反对理由 |
| **D wallet-service（资金域）（推荐）** | 汇率 = **资金换算参数**，语义归属资金域（ADR-035 资金域收口的延续）；wallet 现仅 2 controllers，最轻；trade 快照经 ia-api 新增 `CurrencyClient` Feign 读取（fail-open 哨兵） | ✅ 语义最贴、服务最轻、资金口径单点；快照读取在编排层（`OrderCreationManager` Saga 链内，非事务内 Feign，对齐 09-Constraints） |

**推荐 D + A 组合**：

1. **币种/汇率配置数据 + C 端查询 + 管理端维护 → wallet-service**：C 端 `GET /api/currency/list`（🌐 公开）、管理端 `/api/admin/currency/**`（🔑，`@OperationLog`）、汇率定时拉取 job（scheduler）；网关新增路由（见 §17.6 注记）；
2. **trade 下单快照**：经 ia-api `CurrencyClient`（新增 Feign，fail-open：哨兵 → 不快照 = CNY 订单，主流程零影响）；

4. **币种偏好存储**：**浏览器本地（localStorage + locale 推断），Phase 1 不落 user 域**——偏好是纯前端体验状态，跨设备重选成本近零，落库收益为零；Phase 2 多币种结算时用户币种成为账户属性，届时随结算一并评审落 user 域（O5）。

### 17.5 数据模型草案（草案——规格先行阶段定稿）

> 归属建议 wallet-service（D7/O7）；建表走 Initialize.sql 直改（ADR-045 口径）；技术主键 + 业务唯一键双标识；**金额/汇率均为定点整数**。若 O1 裁决 D1-C，则本节仅保留两表、`orders` 零改动。

**`currency`** — 币种字典（可换算的目标币种；**CNY 不入表**——CNY 是恒定主币种，前端选择器第一项恒为 CNY）：

| 字段 | 类型 | 约束 | 说明 |
| ---- | ---- | ---- | ---- |
| id | BIGINT | PK, AUTO_INCREMENT | 技术主键 |
| code | CHAR(3) | UNIQUE (`uk_currency_code`), NOT NULL | ISO 4217 币种代码（USD/EUR/JPY/KRW…） |
| name | VARCHAR(50) | NOT NULL | 币种名称（美元/日元…） |
| symbol | VARCHAR(8) | NOT NULL | 展示符号（$ / ¥ / ₩…） |
| exponent | TINYINT | NOT NULL | 最小单位指数：目标币最小单位 = 10⁻exponent 主单位（USD=2 分位、JPY/KRW=0 无小数、BHD=3） |
| status | TINYINT | NOT NULL, DEFAULT 0 | 0-停用 1-启用（停用币种不出现在 C 端列表；既有快照订单不受影响） |
| create_time / update_time | DATETIME | NOT NULL | 审计字段（AuditFieldMetaObjectHandler 自动填充） |

**`exchange_rate`** — 汇率（一币种一行，Phase 1 不做历史版本化，O6——历史可审计性由**订单快照列**承载）：

| 字段 | 类型 | 约束 | 说明 |

| id | BIGINT | PK, AUTO_INCREMENT | 技术主键 |

| 字段 | 类型 | 约束 | 说明 |

### 17.7 非功能性需求

1. **金额纪律（最高优先级，硬验收项）**：任何多币种能力**不得引入 `BigDecimal`/`float`/`double`**（金额与汇率一律定点整数：金额 INT 分、汇率 `rate_scaled` BIGINT 定点 10⁻⁶ 刻度）；**不得改动既有 INT 分字段的语义**——核心四金额字段（`totalAmount`/`discountAmount`/`postFee`/`payAmount`）与 `wallet_transaction`/`refund_order`/`reconciliation`/`invoice`/结算金额全程 CNY 分；不变式 V2 `payAmount = totalAmount − discountAmount + postFee` 逐字保持（§17.4.4 守护场景 + 静态检查为验收手段）；`orders` 快照列以 `display_*` 前缀与列注释显式与结算语义隔离。
2. **降级纪律（fail-open 双向）**：汇率端点不可用 → 前端降级仅 CNY 展示（展示型查询返回空值，对齐 ADR-011 三分法）；下单快照读取 → Feign 哨兵 -1 不快照，订单照常创建（**绝不因汇率失败阻塞交易主流程**）；API 拉取失败 → 保留上次成功值 + 告警（stale 但可用）。
3. **换算确定性（可单测）**：换算规则 = 单一公式（D4）+ 统一舍入（half-up 到最小单位），以**可单测的纯函数**实现——Phase 1 前端 TS 模块承载（16-Frontend-Product-Design 定稿），前后端共享**同一组测试向量**（同输入必同输出；算例见 D4/BDD）；Phase 2 若引入服务端换算，按同公式落 ia-common 纯函数（`PostageCalculator`/`PricingCalculator` 先例）并复用同组向量。
4. **免责声明常驻**：所有本币参考价旁固定免责文案（D6），措辞法务审校（O10）；缺失免责文案视为验收不通过。
5. **性能**：P36 币种列表 P95 < 100ms（本地表直读 + 可选 60s 缓存，I44 先例）；展示换算为前端本地整数运算，**零后端开销**；快照读取在 Saga 编排链内增加 ≤1 次 Feign（fail-open，TimeLimiter 5s 内失败即跳过）。
6. **审计**：AD66/AD67 全部 `@OperationLog`（ADR-032 管道一，单行 JSON → logger `AUDIT`）；汇率修正留痕 source/effect_time/updater_id。
7. **数据边界**：汇率/币种为公开参考数据（无 PII，P36 可匿名）；管理端 VO 不含 version/cipher/hash 技术字段（09-Constraints VO 约束）；`/internal/currency/**` 仅集群内 Feign 可达（网关拦截）。

### 17.8 分阶段边界

**Phase 1（本 PRD 评审范围）**：

- 展示换算（前端执行，D7-A）：双价展示 + 币种选择器 + 本地偏好；
- 订单快照锁汇（D1-B，若 O1 采纳）：`orders` 两列 + I60 fail-open 快照 + 订单 VO 增量；
- 币种/汇率管理：`currency`/`exchange_rate` 两表 + P36/I60/AD65-67 草案端点 + 定时拉取 job + 管理端审计；
- 降级：展示回 CNY、快照 fail-open、拉取失败保上次值；
- 明确不含：任何资金链路改动（支付/退款/钱包/对账/发票/结算全 CNY 原样）、后端换算、多语言 i18n。

**Phase 2（roadmap，评审后独立排期；立项条件清单见 D1/§17.2）**：

- **多币种结算**——量化触发器（须同时满足 ≥2 项 + 硬性项全过）：
  - (a) 需求侧：海外注册买家占比 > 10%，或「外币/汇率」关键词客服会话占比 > 5%（连续 90 天）；
  - (b) 供给侧：跨境商家入驻 ≥ 20 家且头部商家明确外币报价意愿；
  - (c) 硬性：跨境收单资质签约（微信跨境/支付宝国际/Stripe/PayPal 至少一家）；
  - (d) 硬性：外汇申报与税基口径（含汇差损益归属）获财务/税务确认；
  - (e) 硬性：渠道按币种扩展/对账币种维度/退款汇差规则/锁汇时点（O4）四项过架构评审。
  - 交付面概述：`pay_order.currency` + 渠道路由扩展 + 对账原币种比对 + 退款汇差入账 + 锁汇时点 + ia-common 服务端换算纯函数；
- 汇率缓冲系数（真换汇成本，O3）、汇率历史版本化（若审计需要，O6）、用户币种偏好落 user 域（O5）。

**明确不做**（Phase 1 与 Phase 2 均不做，除非重新立项评审）：

- **全表 currency 化**（D3-C 反对结论固化——为不存在的收益做全仓伤筋动骨）；
- 商品多币种定价（商家恒 CNY 定价；本币定价化 = Shein 独立站点模式，法人/合规级投入）；
- 多币种钱包余额（`wallet_account`/`wallet_transaction` 恒 CNY 账本）；
- 多币种发票（§十五.9 已定稿不做）；
- BigDecimal/浮点表达金额或汇率（09-Constraints 硬约束）；
- 多语言 i18n 文案与站点（多语言 ≠ 多币种，另案独立评审）。
