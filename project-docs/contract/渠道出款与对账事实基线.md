## 一、微信支付 · 商家转账（出款到零钱）

来源：[发起转账](https://pay.weixin.qq.com/doc/v3/merchant/4012716434)、
[商家转账回调通知](https://pay.weixin.qq.com/doc/v3/merchant/4012712115)、
[错误码](https://pay.weixin.qq.com/doc/v3/merchant/4020801391)

### 1.1 单据状态枚举（官方原文）

| state | 含义 | 是否终态 | 官方给出的处置 |
|---|---|---|---|
| `ACCEPTED` | 转账已受理 | **非终态** | **可原单重试** |
| `PROCESSING` | 转账锁定资金中 | **非终态** | 长时间停留多为余额不足，充值后**原单重试** |
| `WAIT_USER_CONFIRM` | 等待用户确认收款 | 非终态 | 引导用户确认 |
| `TRANSFERING` | 转账中 | 非终态 | — |
| `SUCCESS` | 转账成功 | **终态** | 资金已到账 |
| `FAIL` | 转账失败 | **终态** | **重新生成单据**后再发起 |
| `CANCELING` / `CANCELLED` | 撤销中 / 已撤销 | — | 仅受理中/处理中/待确认/转账中可撤 |

### 1.2 由此必然推出的约束

1. **同步返回不等于终态**：接口 HTTP 200 且 `WAIT_USER_CONFIRM` 只表示"创建成功"，不是转账成功。
2. **存在明确的"非终态"中间态集合**（`ACCEPTED` / `PROCESSING` / `TRANSFERING` / `WAIT_USER_CONFIRM`）——
   系统**不得**把这些态当成失败，也不能当成成功。
3. **"结果未知"是官方承认的正常状态**，不是异常：`ACCEPTED` 允许**原单重试**，
   意味着**同一 `out_bill_no` 可重复提交** ⇒ 幂等由商户单号保证，不是靠"只发一次"。
4. **`FAIL` 之后必须换新单据**（官方原文：重新生成单据并再次发起）⇒ 失败不是"再推一次同一单"。

### 1.3 回调（异步通知）

- 官方明示：**同一通知会多次发送**；处理前先查业务状态，已处理则直接返回成功；
  **必须做数据锁防重入**；未收到回调时**应主动调用查询接口**确认状态。
- **必须验签**（`Wechatpay-Serial` + 平台证书/公钥），并校验通知内容与商户侧信息一致，
  否则会出现"假通知"造成资金损失。

## 二、支付宝 · 单笔转账（出款到支付宝账户）

来源：[转账业务单据查询接口](https://opendocs.alipay.com/open/58a29899_alipay.fund.trans.common.query)、
[常见问题](https://opendocs.alipay.com/mini/009zdx)

### 2.1 官方原文要点

- `alipay.fund.trans.uni.transfer`（单笔转账）返回 **`SYSTEM_ERROR`** 时，
  **必须**用 `alipay.fund.trans.common.query`（转账业务单据查询）查真实结果；
- 判定结果要看响应里的 `status`（转账单据状态）与 `pay_date`（支付时间）等参数。

### 2.2 由此必然推出的约束

1. **同步响应里有"结果未知"错误码**（`SYSTEM_ERROR`）—— 它不是"失败"，是"不知道"；
   直接置失败会造成"钱已出、账记失败"的双重损失。
2. **必须有查询兜底**：转账结果不能只依赖同步返回，也不能只依赖异步通知。

## 三、对账数据来源（账单）

来源：[微信支付 V2 下载资金账单](https://pay.weixin.qq.com/doc/v2/merchant/4011935220)、
[V3 下载账单（服务商）](https://pay.weixin.qq.com/doc/v3/partner/4013080597)

### 3.1 官方原文要点

- 资金账单反映**商户微信账户资金变动**；
- **当日账单次日上午 9 点开始生成，建议 10 点以后获取**；
- 账单下载地址**有效时间 5 分钟**；
- **下载响应的信息请求头中不含签名值 ⇒ 下载账单需跳过验签流程**。

### 3.2 由此必然推出的约束

1. **对账只能是 T+1 的"整日全量拉取"**，不可能实时逐笔 —— 这解释了为什么对账状态机是
   `PENDING → FETCHED → MATCHED|DIFF → RESOLVED`，且**与出款状态机彼此独立**。
2. **下载有"地址 5 分钟过期"** ⇒ 拉取流程必须"先取地址、立刻下载"，不能把地址存起来稍后下。
3. **账单数据是资金视角（账户变动）**，不等于"逐笔状态回执"：一笔转账可能对应账单里的**多条**资金流水
   （锁定、解冻、扣款），所以**按金额匹配必须允许一对多**，不能假设"一单一条"。

## 四、F1 / F2 的判据（事实 → 决策）

### 4.1 F1：渠道形态与对账来源

| 事实 | 推出的结论 |
|---|---|
| 微信/支付宝都有**同步受理 + 异步通知 + 主动查询**三件套 | 单独选"纯同步"**不可行**：同步只到受理态 |
| 回调会**重复投递**，且**可能收不到**（官方要求主动查询兜底） | 必须保留**查询兜底任务**；回调只能是"加速通道" |
| 账单是 **T+1 整日文件**，地址 5 分钟过期 | 对账来源只能是**账单文件**，不能是"实时逐笔比对" |
| `out_bill_no` / `out_biz_no` 是**商户幂等键**，`FAIL` 后要换新单 | 出款必须**自己持有幂等键**，且**失败重发 = 新单据** |

**据此，F1 的现实选项只有两个**（不存在"纯同步"这个选项）：

- **F1-a（推荐）**：**同步受理 + 异步回调 + 定时查询兜底 + T+1 账单对账**（四件全要）；
- **F1-b**：**同步受理 + 定时查询兜底 + T+1 账单对账**（不要回调，少一条链路）。

> 差别只在"要不要接回调"。**回调可以不做，查询兜底和对账不能不做** ——
> 因为官方明说"没收到回调要主动查询"，而账单是资金真相。

### 4.2 F2：`FAILED` 的退款口径

| 事实 | 推出的结论 |
|---|---|
| 微信 `FAIL` 是终态，资金**未成功出账**；重发须**新单据** | 冻结资金应**回到可提现**，但必须是**新单据重发**，不是"重试旧单" |
| `ACCEPTED` 可**原单重试**；`PROCESSING` 充血后原单重试 | 「未知态」**绝对不能**判失败、更不能解冻 —— 否则重复出款 |
| 支付宝 `SYSTEM_ERROR` 是"未知"，须查询确认 | 同上：未知态只能"等/查"，不能"判失败" |

**据此，F2 的口径应当分层，而不是一刀切**：

| 渠道态 | 资金处置 | 是否自动 |
|---|---|---|
| `SUCCESS` | 冻结转已付（`frozen → paid_total`） | 自动 |
| `FAIL`（渠道明确失败） | 冻结**回到可提现**（`frozen → 0`），**须新单据重发** | **可自动解冻**（渠道已明确） |
| `ACCEPTED` / `PROCESSING` / `WAIT_USER_CONFIRM` / `TRANSFERING`（未知态） | **不动**，停在 `PAYING` | **禁止自动**，只告警 + 查询 |
| 超过阈值仍未知 | 人工介入（现有 B1 停留告警） | 人工 |
| 支付宝 `SYSTEM_ERROR` | 先查询；查不到则同"未知态" | 禁止自动 |

> 这修正了当前"`FAILED` 一律不自动释放"的粗糙裁决：**明确失败可以自动解冻，未知态才必须人工**。
> 两者混为一谈的代价：要么让用户白等（该解冻的不解冻），要么重复出款（该等的不等）。

## 七、决策定稿（2026-10-19）

### 7.1 F1：设计选 **F1-a**，先跑 **F1-b**

| | 内容 | 何时 |
|---|---|---|
| **设计口径** | 同步受理 + 异步回调 + 定时查询兜底 + T+1 账单对账 | 架构按此设计，**回调通道留位** |
| **先跑口径** | 同步受理 + 定时查询兜底 + T+1 账单对账 | 第一期只落这三件 |

**两方案共同前提：端口必须提供 `query()`。**
理由：两方案的差别只在"有没有回调"，而**查询兜底是共有的**；
`query()` 不先落，F1-b 根本跑不起来，F1-a 的回调也要靠它做补偿。
⇒ `WithdrawalPayoutPort` 增加查询能力（按商户幂等键查渠道终态），先落 `query()`，再谈回调。

### 7.2 F2：分层处置 + 两条硬边界

分层（已认可）：

| 渠道态 | 资金 | 自动? |
|---|---|---|
| `SUCCESS` | 冻结 → `paid_total` | 自动 |
| **渠道明确 `FAIL`** | 冻结回到可提现，**且必须换新 `payoutNo`** | 可自动 |
| 非终态（`ACCEPTED`/`PROCESSING`/`WAIT_USER_CONFIRM`/`TRANSFERING`） | 不动，停在 `PAYING` | 禁止自动 |

**硬边界一：自动解冻必须绑定「换新 `payoutNo`」。**
解冻与重发是**同一件事的两面**：解冻后若沿用旧 `payoutNo`，等于把"已知失败"的单号再送一次，
而官方明确 `FAIL` 后**须重新生成单据** —— 沿用旧单号违反渠道契约，且一旦渠道侧旧单号有残留状态，
就可能出现"解冻 + 再扣一次"的双重扣减。
⇒ 规则：**解冻 = 作废旧 `payoutNo` + 生成新 `payoutNo`**，两者在同一事务内完成，缺一不可。

**硬边界二：`CANCELLED` 与 `SYSTEM_ERROR` 都不许按 `FAIL` 处理。**

| 态 | 为什么不能当 FAIL |
|---|---|
| `CANCELLED` / `CANCELING`（微信） | 撤销是**我方或用户主动终止**，资金并未"失败出账"；且撤销有"撤销中"中间态，撤销结果仍需查询确认 —— 当 FAIL 会误判成渠道失败，还可能触发一次不该有的重发 |
| `SYSTEM_ERROR`（支付宝） | 官方原文明确它是**未知**（须用 `alipay.fund.trans.common.query` 查真实结果）。当 FAIL 就是"钱可能已经出去了，账却记成失败" |

⇒ 二者一律进**未知态**：停在 `PAYING`、只告警 + 查询，**不解冻、不重发**。

### 7.3 前置：`payoutNo` 从「一提现一单号」改为「一提现可多单号」

**这是 F2 落地的硬前置**（F2 的"换新单号"在单号模型下无法表达）。详见 §八。

## 八、`payoutNo` 多单号模型（设计草案，待确认后实现）

### 8.1 问题

现状 `withdrawal.payout_no` 是**单值列**，语义是"这笔提现的出款单号"。
但渠道契约要求：**一次失败后必须用新单据重发**（微信 `FAIL` 原文），
支付宝同样以 `out_biz_no` 做幂等 —— 沿用旧号即违反契约。
⇒ 一笔提现**天然会有多个出款单号**（每次尝试一个），单值列表达不了。

### 8.2 模型

| 位置 | 内容 |
|---|---|
| 新表 `withdrawal_payout_attempt` | `id` / `withdrawal_id` / `payout_no`（唯一） / `state` / `channel_ref` / `requested_at` / `finished_at` / `channel_message` / `create_time` |
| 唯一键 | `uk_payout_no (payout_no)`；`uk_withdrawal_attempt (withdrawal_id, attempt_no)` —— 尝试序号保证可追溯 |
| `withdrawal` 表 | **保留** `payout_no` 作为"**当前有效尝试**"的冗余指针（查询与对账用），但**真相在尝试表**；另保留 `last_payout_attempt_at` / `last_payout_result` |
| 状态 | 尝试态：`REQUESTED` → `UNKNOWN` / `SUCCESS` / `FAILED` / `CANCELLED`；提现单态不变（`PAYING` / `PAID_OUT` / `FAILED`） |

### 8.3 关键规则

1. **一次尝试一个单号**：每次向渠道发起前先落一行 `attempt`，`payout_no` 由系统生成；
2. **换号即新尝试**：`FAIL` → 解冻 + 生成新 `attempt`（新 `payout_no`），**禁止复用**旧号；
3. **`UNKNOWN` 可持续存在**：非终态/`SYSTEM_ERROR`/`CANCELLED` 落 `UNKNOWN`，由查询任务收敛；
4. **对账按单号对齐**：渠道账单里一行对一个 `payout_no`，多尝试天然支持"一笔提现对多行"；
5. **旧列兼容**：`withdrawal.payout_no` 只写"当前有效尝试"的单号，历史尝试**只能**从尝试表读 —— 不许把历史压在单值列里。

### 8.4 数据迁移（无存量数据，直接改结构）

`Initialize.sql` 直接改：新增 `withdrawal_payout_attempt` 表；
`withdrawal.payout_no` 注释改为"当前有效尝试的单号（真相在尝试表）"。

### 8.5 待确认（实现前必须拍板）

1. 尝试表是**一张**还是按渠道拆（建议一张，渠道差异放 `channel` 列）；
2. `withdrawal.payout_no` 是否保留为冗余指针（建议保留：对账与报表高频读）；
3. `attempt_no` 从 1 递增是否够（是否需要 `(withdrawal_id, payout_no)` 双唯一）。

## 九、`payoutNo` 生成逻辑变更的影响面（建表前核实，2026-10-19）

### 9.1 现状（实测）

> **`payoutNo` 当前 == `withdrawalNo`**：`WithdrawalPayoutService` 原文注释
> 「重试复用同一个 payoutNo（withdrawalNo）：渠道侧去重的唯一依据」。
> 即"一提现一单号"不是约定，是**直接复用了提现单号**。

引用 `payoutNo` / `payout_no` 的地方（trade-service 内，共十三处源文件）：

| 层 | 文件 | 用法 | 变更影响 |
|---|---|---|---|
| 端口 | `WithdrawalPayoutPort` | `PayoutCommand.payoutNo`；契约写"同一提现单只生成一次" | **契约要改**：同一**尝试**内不变；新尝试必须新号 |
| 应用 | `WithdrawalPayoutService` | 复用 withdrawalNo 作 payoutNo；`lastResult(payoutNo)` | **生成逻辑改为「提现单号 + 尝试序号」**；结果落 attempt |
| 应用 | `PayoutStaleAlerter` | 去重键 `payoutNo + gen`；告警体带 payoutNo | 多尝试后**同一提现单会有多个单号**，去重键需确认按"当前尝试"即可（停在 PAYING 的恰是当前尝试） |
| 领域 | `WithdrawalRepository` | `claimPaying(id, payoutNo)`、`markAlertedOnce(payoutNo, gen)`、`findPayoutResult(payoutNo)`、`StalePaying.payoutNo` | 语义从"提现单号"变"尝试号"；结果读写要指向 attempt 行 |
| 领域 | `WithdrawalReconciliationComparer` | `Ours(payoutNo, …)` 作为我方侧输入 | **对账单位从"提现单"变"尝试"** ⇒ 一笔提现天然可对账单多行（与 §3.2 一致） |
| 适配 | `ManualPayoutAdapter` / `MockPayoutAdapter` | 幂等表以 payoutNo 为键 | 逻辑不用改；语义从提现单号变尝试号 |
| 持久化 | `WithdrawalPO` / `WithdrawalMapper` / `WithdrawalRepositoryImpl` | `payout_no` 列读写 | 改为写"当前有效尝试的派生指针" |
| 持久化 | `ReconciliationItemPO` / `ReconciliationRepositoryImpl` | 已按 `payout_no` 逐笔存 | **无需改**：`uk_batch_item(batch_no, payout_no, channel_ref)` 天然支持一笔提现多行 |
| DDL | `Initialize.sql:788`（列）、`:799`（`uk_payout_no`）、`:1573/1617`（告警账、对账逐笔） | — | 列注释改语义；`uk_payout_no` 保留 |

### 9.2 生成规则（已实测，定稿见 §十）

~~`payoutNo = withdrawalNo + "-" + attemptNo`~~ —— 实测后**否决**（见 §十：`withdrawalNo` 本身已 32 字符）。

### 9.3 建表前必须确认的三条（已拍板的部分）

1. ✅ **尝试表一张**，渠道差异放 `channel` 列（不按渠道拆表）；
2. ✅ `withdrawal.payout_no` **保留为派生指针**：指向"当前有效尝试"，
   **写入与 attempt 行同事务**，并加**校验等式**：
   `withdrawal.payout_no == attempt(当前有效).payout_no AND attempt.withdrawal_id == withdrawal.id`；
   该等式要有**真库用例**（不只写在注释里）验证；
3. ✅ 唯一键**两层，不要双唯一**：`UNIQUE(payout_no)` 全局 + `UNIQUE(withdrawal_id, attempt_no)`；
   **不加** `(withdrawal_id, payout_no)` —— 它被前两者蕴含，多余约束只会增加写入失败面。

### 9.4 尚未确认（阻塞建表）

- `attemptNo` 是否**只增不减**（撤销后是否复用序号）—— 涉及与渠道"撤销后重新发起"的对齐；
- `payoutNo` 长度实测（依赖 `withdrawalNo` 字符串形态的确切位数）；
- 告警去重键是否要从 `payoutNo` 换成 `withdrawalId + attemptNo`（取决于是否允许同一提现单多尝试同时停在 PAYING —— 按规则应当不可能，但要有一条用例证明）。

## 十、`payoutNo` 生成规则定稿（2026-10-19，实测后）

### 10.1 实测

- `withdrawalNo` 为 `String`，由 `IdGenerator.nextId()` 产生；
- `IdGenerator.nextId()` 实现为 `HEX.formatHex(bytes)`，源为 **16 字节**随机/时间序列
  ⇒ 字符串**固定 32 字符**（十六进制，每字节两位）。

**结论**：`withdrawalNo + "-" + attemptNo` 至少 34 字符，**超过 32 字符阈值** ⇒ 按既定规则改用「**短哈希 + 序号**」。

### 10.2 定稿格式

```
payoutNo = shortHash(withdrawalNo) + "-" + attemptNo
        例： 9f3ac1b27e0d4a56-1        （短哈希 16 位十六进制 + 连字符 + 序号）
长度：16 + 1 + len(attemptNo)  ⇒ attemptNo 为个位数时 18 字符，千位以内仍 ≤ 22
```

- **短哈希取 `SHA-256(withdrawalNo)` 的前 16 位十六进制**（64 bit）；
- **不反解提现单**：`payoutNo` 不再能反推 `withdrawalNo` —— 这是有意的取舍（见 10.3）；
- 渠道只把 `payoutNo` 当**不透明幂等键**，反解与否对外无影响。

### 10.3 冲突与可追溯性

- **冲突**：64 bit 空间，业务量级下碰撞概率可忽略；即便发生，`UNIQUE(payout_no)` 会**写失败**，
  由"新尝试"路径重取（换序号）即可 —— 不设静默重试，冲突必须可见；
- **可追溯**：`payoutNo` 不可反解 ⇒ 排查靠 `withdrawal_payout_attempt` 表
  （`payout_no` → `withdrawal_id` → `withdrawal_no`），这是尝试表存在的另一个理由。

### 10.4 `attemptNo` 规则（拍板）

- **只增不减、生成即占号**：每次向渠道发起**之前**先生成并落库，`attempt_no` 单调递增；
- **任何终态之后的重新发起都是新尝试**（`FAILED` / `CANCELLED` / `SUCCESS` 之后均不得复用序号）；
- 撤销**不复用**序号 —— 取消也是一次尝试，占号后即作废；
- 由此保证：`attempt_no` 的集合就是"向渠道发起过的次数"，可作为审计计数直接使用。

### 10.5 告警去重键（拍板）与配套不变量

- **保持 `payout_no + alert_gen` 不变**（不改成 `withdrawalId + attemptNo`）；
- 依据：停在 `PAYING` 的永远是**当前有效尝试**，而当前有效尝试的 `payout_no` 是唯一的
  ⇒ 以 `payout_no` 去重等价于"按尝试去重"，且不会因换尝试而丢失告警；
- **必须补一条不变量用例**：**「同一提现单最多只有一个非终态尝试」**
  （即不存在两个 `UNKNOWN`/`REQUESTED` 状态的 attempt 行属于同一 `withdrawal_id`）。
  这条不变量是上面"去重键可保持不变"的**唯一前提** —— 没有它，换键就是必须的。
  用例形式：构造两次并发发起，断言第二次因不变量而被拒（或断言查询结果集大小为一）。

### 10.6 建表所需字段（汇总，供实现）

`withdrawal_payout_attempt`：`id` / `withdrawal_id` / `attempt_no` / `payout_no` / `channel` /
`state`（`REQUESTED` / `UNKNOWN` / `SUCCESS` / `FAILED` / `CANCELLED`）/ `channel_ref` /
`channel_message` / `requested_at` / `finished_at` / `create_time` / `update_time`；
`UNIQUE(payout_no)` + `UNIQUE(withdrawal_id, attempt_no)`（**两层，不双唯一**）。

## 十一、实现约束（第 2/3/5 步，逐条拍板）

### 11.1 第 2 步：`ManualPayoutAdapter.query()` 返回 `UNKNOWN`，且 resume job 跳过人工渠道

人工渠道（线下转账）**没有可查询的渠道状态** —— 假装能查会造出一个永远查不到的循环。
⇒ `query()` 必须返回 `UNKNOWN`（"我不知道"，不是"成功/失败"），
并且 **resume/查询兜底任务对 `channel = MANUAL` 直接跳过**，只由人工录入结果收尾。

> 这不是"先空着"：把"无从查询"显式建模成 `UNKNOWN`，比返回 `SUCCESS` 或抛异常都正确 ——
> 前者会错判资金到账，后者会让任务每次都红。

### 11.2 第 3 步：`claimNewAttempt` 必须 `SELECT ... FOR UPDATE` 锁提现单行

「同一提现单最多一个非终态尝试」这个不变量，**靠应用层先查后插在并发下不成立**
（两个线程同时查到"没有非终态"，然后各插一行）。
⇒ 占号必须**先锁 `withdrawal` 行**（`SELECT ... FOR UPDATE`），
在锁内完成"查非终态 + 取 max(attempt_no) + 1 + 插入"三件事，然后才向渠道发起。
用例：并发两步发起，断言**只有一次成功占号**，另一次被不变量拒绝。

### 11.3 第 5 步：`FAIL` 自动解冻必须带重试上限

没有上限的"失败即解冻 + 重发"就是一个**无限重试器**：渠道持续失败时会不停解冻/占号/发起，
把渠道打爆、把尝试表撑爆，还可能触发渠道风控。
⇒ 规则：**同一提现单的尝试次数上限**（建议 3），达到后**停止自动重发**，
状态留在可人工介入的显式失败，并走告警 —— 与"停留告警"是同一套人工兜底思路。
用例：连续失败达上限后，断言不再产生新尝试、且告警被触发。

## 十二、第 3 步前置：H2 锁实验与四项确认（2026-10-19）

### 12.1 实验结论：H2 的 `SELECT ... FOR UPDATE` **真的阻塞**

`LockSemanticsH2Test`（`MODE=MySQL`，两条连接）：
T1 取 `FOR UPDATE` 后，T2 设 300ms 锁超时再取同一行 ⇒ **抛锁超时且实际等待 ≥250ms**；
T1 回滚释放后，T2 立即取到锁。

⇒ **并发用例可以是真并发**，不必退化成"串行等价"。这条实验本身就是资产：
以后任何"靠行锁保证的不变量"，都要先跑它，否则并发用例可能在本机永远绿、上生产才爆。

### 12.2 四项确认

| # | 确认 | 落点 |
|---|---|---|
| 1 | H2 `FOR UPDATE` 阻塞 —— **已实验证明** | `LockSemanticsH2Test`（长期保留） |
| 2 | `claimNewAttempt` **必须 `@Transactional` 且无自调用** —— 锁只在事务内有效；同类调用绕过代理则锁形同未取 | 写进端口类注释第 2 条 |
| 3 | 撞 `UNIQUE(withdrawal_id, attempt_no)` **直接抛，不在同事务重试** —— 锁已保证串行，撞键只说明**有代码绕过了锁**，重试会把 bug 藏起来 | 写进端口类注释第 3 条 |
| 4 | 重试上限收敛在 `claimNewAttempt`；**上限只约束 `FAILED` 自动重试**，撤销后的重发不计入 | 见 12.3 |

### 12.3 上限口径（含 `CANCELLED`）

- **只对 `FAILED` 计数**：连续失败达上限 ⇒ 停止自动重发，停在人工可介入的显式失败 + 告警；
- **`CANCELLED` 不计入**：撤销是**主动终止**（我方或用户），不是"渠道不认"，把撤销算进失败上限
  会让"撤销后重新发起"被误拦 —— 用户主动取消后想再提，不该被判成"失败太多次"。
- 但**同提现单的「非终态唯一」不变量仍然适用**：撤销也必须先把尝试收敛到终态（`CANCELLED`），
  才能占下一个号。

### 12.4 `updateState(payoutNo, from, to)` 已定义（只定义不实现）

给 `query()` 的写回一个落点：**只改状态、不碰资金**（资金处置在应用层按 §7.2 决定）。
条件更新语义：0 行 = 状态已变或单号不存在，**调用方必须区分**（否则会把并发写回误判成"单号丢了"）。

## 十三、第 4 步核实结果与一处次序矛盾（2026-10-19）

### 13.1 四项确认

| # | 确认 | 落点 |
|---|---|---|
| 1 | 第 4 步范围 = **接入 + attempt 状态机**；`pay` 异常路径置 **`UNKNOWN`** 而不是 `REQUESTED` | 否则 resume job 会认为"没发出过"而**重复出款** |
| 2 | `markPayoutAttempt` 现在写的是 **`withdrawal.last_payout_attempt_at`**（提现单表） | 所以"与 `claimNewAttempt` 同一事务"意味着**跨两张表**：attempt 插入 + 提现单打标 |
| 3 | 依赖 `payoutNo == withdrawalNo` 的**硬断言只有一处**：`WithdrawalPayoutServiceTest:79` | 测试侧共有 7 个文件引用 `payoutNo`，但只有这一处断言等值 |
| 4 | 校验等式放**定时任务 + 真库用例**，不放线上读路径 | 线上每次读都做等式校验会把"数据不一致"变成"读失败"，反而扩大故障面 |

### 13.2 矛盾：`payoutNo` 里含序号，但序号在锁内才确定

- 端口签名是 `claimNewAttempt(withdrawalId, payoutNo, channel, now)` —— **单号由调用方先给**；
- 但单号 = `短哈希(withdrawalNo) + "-" + attemptNo`，而 `attemptNo` **必须在行锁内**由 `max(attempt_no)+1` 得出；
- 调用方在锁外无法知道序号 ⇒ 按现签名**无法生成单号**。

**处置（建议，待确认）**：把端口改成注入**单号工厂**，把"取号"与"生成"解耦：

```java
Attempt claimNewAttempt(Long withdrawalId, String channel,
                        java.util.function.IntFunction<String> payoutNoFactory,   // attemptNo -> payoutNo
                        LocalDateTime now);
```

- 生成规则仍在 domain（`PayoutNoGenerator`），仓储**只负责在锁内把序号交给工厂**；
- 好处：单号唯一性/长度规则不外泄到仓储，序号又一定来自锁内；
- 代价：端口签名略抽象，需要用注释写清"工厂必须是纯函数"。

### 13.3 状态机（第 4 步要落的）

```
claim（锁内插入）  →  REQUESTED
pay 成功受理       →  保持 REQUESTED（受理 ≠ 到账，等 query/回调收敛）
pay 抛异常/超时    →  UNKNOWN      ← 关键：不是 REQUESTED，否则 resume 会重复出款
query = SUCCESS    →  SUCCESS
query = FAILED     →  FAILED（可换号重发，受上限约束）
query = CANCELLED  →  CANCELLED（不计入失败上限）
query = UNKNOWN    →  保持 UNKNOWN
```

## 十四、第 4 步签名定稿（2026-10-19）

### 14.1 单号工厂（不用 `IntFunction`）

```java
@FunctionalInterface
public interface PayoutNoFactory {
    /** 纯函数：同一 (withdrawalNo, attemptNo) 必须得到同一单号。 */
    String create(String withdrawalNo, int attemptNo);
}

Attempt claimNewAttempt(Long withdrawalId, String channel, PayoutNoFactory factory, LocalDateTime now);
```

- 仓储在**锁内**先取 `withdrawal_no`（与行锁同一条 `SELECT ... FOR UPDATE`），
  再把 `(withdrawalNo, attemptNo)` 交给工厂 —— **Service 全程不碰 `withdrawalNo`**；
- 用专用函数式接口而不是 `IntFunction<String>`：`IntFunction` 只带序号，拿不到提现单号；
  而专用接口能把"纯函数"这条约束**写在类型上**（名字+注释），比靠口头约定强。

### 14.2 纯函数约束的三重保证

1. **domain 层**：`PayoutNoGenerator` 是 `final` 类 + 静态纯函数，无状态、无 I/O；
2. **ArchUnit 断言**：`PayoutNoFactory` 的实现不得引用仓储/端口/时钟等有副作用类型
   （守卫落在架构层，违反即红）；
3. **异常回滚用例**：工厂抛异常时，`claimNewAttempt` 的整个事务回滚 —— attempt 未插、提现单未打标。

### 14.3 `PayoutResult` 必须补 `terminal`

现有 `PayoutResult(accepted, channelRef, reason)` 表达不了"**已到终态**"：
人工渠道（钱已在系统外转出）是**终态成功**，但 `accepted=true` 会被上层当成"受理态"，
永远卡在 `REQUESTED`。

```java
record PayoutResult(boolean accepted, boolean terminal, String channelRef, String reason) {}
```

映射：`Manual` ⇒ `accepted=true, terminal=true`；mock `ACCEPTED` ⇒ `false/true` 按渠道语义填
（受理未到账 ⇒ `terminal=false`）；`REJECTED` ⇒ `accepted=false, terminal=true`；
`TIMEOUT` / 异步未到点 ⇒ `accepted=false, terminal=false`（未知，等 query）。

## 十五、第 4 步：基线、构造点与事务边界（2026-10-19 实测）

### 15.1 第 0 步 基线

`mvn -o -pl trade-service test` ⇒ **全绿**（作为改动前的对照基线）。

### 15.2 第 2 步：`PayoutResult` 构造点共五处，四种组合写进注释

| 构造点 | accepted | terminal | 语义 |
|---|---|---|---|
| `ManualPayoutAdapter` | true | **true** | 人工渠道：钱已在系统外转出 ⇒ **终态成功** |
| `MockPayoutAdapter` REJECTED | false | **true** | 明确拒绝 ⇒ 终态失败（可换号重发） |
| `MockPayoutAdapter` TIMEOUT | false | **false** | 超时 = 未知，等 `query()` |
| `MockPayoutAdapter` ASYNC 未到点 | false | **false** | 等回执 = 未知 |
| `MockPayoutAdapter` 受理成功 | true | **false** | **受理 ≠ 到账**，等 `query()`/回调 |

**四种组合的含义（注释里要写死）**
- `accepted=true, terminal=true` ⇒ 直接收敛成功，不再等查询；
- `accepted=true, terminal=false` ⇒ 保持 `REQUESTED`，交给查询收敛；
- `accepted=false, terminal=true` ⇒ 明确失败，可换号重发（受上限）；
- `accepted=false, terminal=false` ⇒ 置 **`UNKNOWN`**，**不得**当失败解冻、**不得**当未发出重发。

### 15.3 第 3 步：`markPayoutAttempt` 确认不是 `REQUIRES_NEW`

- **全仓 grep `REQUIRES_NEW` 为空** —— 没有任何方法强制新事务；
- `markPayoutAttempt` 就是一条 `UPDATE withdrawal SET last_payout_attempt_at = ? WHERE id = ? AND status = 4`
  ⇒ **运行在调用方事务里**，条件带 `status = 4`（`PAYING`）。
- `WithdrawalPayoutService.settle()` **没有** `@Transactional`（类注释已写明：调外部接口的方法不得进事务）
  ⇒ 事务边界必须由**仓储层小事务**提供，而不是包住 `pay()`。

### 15.4 第 4 步的三段事务边界（据此落）

```
事务A（仓储层小事务）: claimNewAttempt（锁提现单行 + 插 attempt）
                      + markPayoutAttempt（打标）
                      + 写 withdrawal.payout_no 派生指针
     —— 三者必须同事务：否则出现「有尝试没打标」「有指针没尝试」
事务外:            payoutPort.pay(...)        ← 远程调用，绝对不能进事务
事务B（仓储层小事务）: terminal=true  → 收敛 attempt 状态
                      terminal=false → 置 UNKNOWN
```

**`terminal=false` 时禁止调用 `completePayout`** —— 那会把"未知"直接记成已打款（钱可能还没出去）。

### 15.5 第 1 步补充：工厂"不得捕获可变状态"

`ArchUnit` **兜不住 lambda**：lambda 体内捕获的外部局部变量在字节码里表现为合成字段/参数，
规则写不出可靠的判据。因此这条靠**三重保证**中的另两层兜：
- **domain 层**：`PayoutNoGenerator` 为 `final` 静态纯函数，本就无可捕获；
- **异常回滚用例**：工厂抛异常 ⇒ 整个 `claimNewAttempt` 回滚（attempt 未插、提现单未打标）。
  这条用例能抓到"工厂里做了写操作"的多数情形。
- 文档层面**明确写出**："工厂不得捕获可变状态；它必须是 `(withdrawalNo, attemptNo) → 单号` 的纯映射。"
