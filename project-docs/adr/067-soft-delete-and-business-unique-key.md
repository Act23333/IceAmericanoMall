# ADR-067: 软删与业务唯一键共存 —— 占用位必须显式清理（`invoice_title.uk_user_default` 口径）

- **状态**：已采纳（2026-10-19，U6）
- **影响面**：`trade-service` 发票抬头（`invoice_title`，INV6–INV9）、`Initialize.sql`、票据一族的新表设计
- **关联**：ADR-045（结构真相源）、ADR-050（`BINARY(16)` 业务键）、`collaboration/09-constraints.md`（软删规则）

## 背景

「一用户至多一条默认抬头」这个业务不变量，这里由**唯一键**承载，而不是由代码判断：

```sql
`is_default` TINYINT NULL COMMENT '1=默认抬头；uk_user_default 多 NULL → 一用户至多一条默认',
`deleted`    TINYINT NOT NULL DEFAULT 0 COMMENT '软删标记（@TableLogic）',
UNIQUE KEY `uk_user_default` (`user_id`, `is_default`),
```

利用的是 MySQL「唯一索引对 NULL 不判重」的语义：非默认行把 `is_default` 留 **NULL**（无论多少行都不冲突），
默认行填 **1**（同一 `user_id` 至多一行）。这比「应用层先查后写」强：并发下前者由存储引擎拒绝，
后者必错在「查与写之间」。

但同一张表又启用了 `@TableLogic` 软删。两个机制叠在一起，产生三条**反直觉**的结论 ——
它们都不是 bug，但每一条都能让后来者「顺手改对」而后静默出错。

## 决策

### 1. 默认位是**占用位**：写默认之前必须清旧默认，且清理**不得**过滤 `deleted`

`InvoiceTitleMapper#clearDefaultByUserId` 是：

```sql
UPDATE invoice_title SET is_default = NULL WHERE user_id = #{userId} AND is_default = 1
```

**没有 `AND deleted = 0`，这是承重设计，不是遗漏。** 原因：

- 软删**不**清 `is_default`（见决策 2）⇒ 一条被软删的默认抬头，其行仍占着 `(user_id, 1)` 这个唯一槽位；
- 若清理语句加了 `deleted = 0`，它就**看不见这一行**，槽位继续被占；
- 随后插入新默认行 ⇒ 唯一键冲突，用户看到的是「设默认失败」，而库里那一行他**已经删掉了**（列表里看不见）。
  这是最坏的一种缺陷形态：**用户操作与报错原因在界面上无法对应**。

⇒ 判据：**「清理占用位」语句的语义是「把这个位置腾出来」，因此必须覆盖所有占位行（含已软删的）**；
把它当成「更新可见数据」来加 `deleted = 0`，等于把腾位置改成了「只腾看得见的」。

### 2. 软删**不**清 `is_default`（保留事实，便于恢复与审计）

软删的语义是「用户不再看它」，不是「它从未存在」。清掉 `is_default` 会让「恢复该抬头」变成
「恢复到哪一行、要不要重新设默认」这种需要二次询问的状态；保留则恢复动作只需处理**占用冲突**
（见决策 1），不涉及状态重建。

### 3. 自定义 SQL 一律自带 `deleted = 0`；MP 注入 SQL 由 `@TableLogic` 负责

两类 SQL 的口径**不同**，这是本 ADR 最容易被踩的一条：

| SQL 来源 | 谁负责软删过滤 | 写新 SQL 时要做的事 |
| :-- | :-- | :-- |
| MP 注入（`selectById` / `updateById` / `delete(wrapper)`） | `@TableLogic` 自动追加 | 什么都不用做 |
| **自定义注解 SQL**（`@Update` / `@Select`） | **没人负责** | **必须自己写 `deleted = 0`** |

本表两处正反例并存，且都刻意如此：

- `updateTitleById`（全量更新）**带** `AND deleted = 0` —— 若不带，一次编辑就能「复活」已软删的抬头；
- `clearDefaultByUserId`（腾占位）**不带** —— 理由见决策 1。

⇒ 判据（写 SQL 前先问一句）：**这条语句是「改用户看得见的数据」，还是「腾一个位置」？**
前者带 `deleted = 0`，后者不带。**不要**为了「风格统一」把两者改成一样 —— 那一定会改错其中一条。

### 4. 唯一键里**不放** `deleted`

另一种常见做法是 `UNIQUE (user_id, is_default, deleted)`。本项目**明确不采用**：

- 它把「软删后可以再建一条同名/同默认」变成合法 —— **唯一性在软删后静默失效**，
  于是「至多一条默认」这条不变量只在「都没删」时成立；
- 它把「恢复」变成「可能与现存行撞车」的第二种冲突形态，比决策 1 的占用冲突更难解释。

⇒ 唯一性靠**占用位**维护，不靠把 `deleted` 塞进键里。

## 后果

- **正面**：不变量由存储引擎保证；并发「两人同时设默认」由唯一键拒绝（有界失败，不会双默认）；
  写默认的两个入口（`createTitle` / `updateTitle`）同事务执行「清旧 → 写新」，窗口内有键兜底。
- **代价（登记，不假装已解决）**：
  1. **恢复软删的默认抬头**必须先清默认位，否则撞车 —— 当前**没有**「恢复」端点（INV6–INV9 只做增删改查），
     故该路径暂不可达；一旦新增恢复入口，**必须**按决策 1 先清再恢复。
  2. **并发下的用户观感**：「两人几乎同时设默认」时，后到者可能收到唯一键冲突（500 或按业务码收敛），
     而不是「你被覆盖了」。当前按「异常向上透出」处理，**未做**友好文案 —— 属文案问题，不改不一致性。
  3. **新表复制这套模型时必须同步本 ADR 的三条判据**（清理不过滤软删 / 自定义 SQL 自带 `deleted = 0` /
     键里不放 `deleted`），否则会出现「同一套写法、两种语义」的局部实现。

## 一次自我纠正（留档）

本条在交接单里原本写作「`clearDefaultByUserId` 不带 `deleted = 0`，**恰好**没踩坑 ——
"对的但是偶然的"」。**这个描述是错的**：它不是偶然对，而是**必须**不对。
把它当偶然，下一个人就会「顺手补上 `deleted = 0`」以消除这份不安 ——
那正是决策 1 描述的缺陷。⇒ 教训：**看到一处「不一致」时，先判断它是遗漏还是承重**；
写不清理由的那一处，才是真的遗漏。
