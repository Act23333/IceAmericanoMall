# 05 — 领域建模方法 (DDD 战术设计)

## 一、目的与产出

**本阶段解决什么问题**：将 PRD 中的业务概念转化为与技术无关的领域模型，建立团队对业务逻辑的统一认知。

**输入**：PRD（功能列表） + Architecture Document（限界上下文） + 用例图

**输出**：

- 限界上下文 + Context Map
- 实体 (Entity) + 属性
- 值对象 (Value Object)
- 聚合 (Aggregate) + 聚合根 (Aggregate Root)
- 领域服务 (Domain Service)
- 通用语言词汇表 (Ubiquitous Language)

**产物文档类型**：DDD Domain Model Document (参考 Eric Evans《领域驱动设计》)

## 二、方法论步骤

### 步骤 1：确认限界上下文

限界上下文已在 Architecture 阶段初步划分。此阶段确认每个上下文内的模型边界。

### 步骤 2：识别实体

**实体特征**：

- 有唯一标识（业务标识，不是数据库 ID）
- 有生命周期，状态会变化
- 需要被持续追踪

**方法**：从需求描述中找名词，判断是否有独立标识和生命周期。

| 名词  | 是实体？ | 理由                  |
| --- | ---- | ------------------- |
| 用户  | ✅    | 有唯一标识 (userId)，状态可变 |
| 地址  | ✅    | 有唯一标识，可独立 CRUD      |
| 金额  | ❌    | 无独立标识，是属性 → 值对象     |

### 步骤 3：区分实体与值对象

| 维度   | 实体 (Entity)          | 值对象 (Value Object)           |
| ---- | -------------------- | ---------------------------- |
| 标识   | 有唯一标识                | 无标识，由属性值定义相等性                |
| 可变性  | 可变                   | 不可变（推荐）                      |
| 生命周期 | 有                    | 依附于实体                        |
| 例子   | User, Order, Product | Money, Address(快照), SpecDesc |

### 步骤 4：划定聚合

**聚合**是一组相关对象的集合，有一个聚合根作为入口。

**聚合设计原则**：

- 聚合根是唯一对外暴露的入口
- 聚合内对象通过聚合根访问（「引用聚合根」原则）
- 一个事务只修改一个聚合
- 小聚合优于大聚合

**识别方法**：

1. 找到业务上的「整体-部分」关系（订单-订单项）
2. 判断不变量（订单总额 = 订单项小计之和）
3. 聚合根通常是最常被引用的那个实体

### 步骤 5：提取领域服务

当业务逻辑不属于任何单一实体时，提取为领域服务：

> 领域服务是「无状态的、以业务动作为核心的操作」

| 候选              | 是领域服务？ | 理由               |
| --------------- | ------ | ---------------- |
| PasswordEncoder | ✅      | 密码加密不属 User 实体自身 |
| TokenService    | ✅      | JWT 签发涉及密钥、过期策略  |
| StockManager    | ✅      | 库存扣减涉及并发控制       |

### 步骤 6：建立通用语言词汇表

团队统一术语，中英对照，避免「订单」在不同上下文中含义不同。

## 三、冰美商城实践示例

### 限界上下文划分

```
用户上下文 ─── 商品上下文 ─── 订单上下文
   │               │              │
认证上下文     搜索上下文     支付上下文
                              │
                           物流上下文
```

### 核心聚合

| 聚合  | 聚合根     | 内部实体            | 不变量          |
| --- | ------- | --------------- | ------------ |
| 用户  | User    | Address (1:N)   | 一个用户最多成为一个商家 |
| 商品  | Product | SKU (1:N)       | 库存不能为负       |
| 订单  | Order   | OrderItem (1:N) | 总额 = 各小计之和   |

| 中文  | 英文               | 定义         |
| --- | ---------------- | ---------- |
| 待付款 | Pending Payment  | 订单已生成等待支付  |
| 待发货 | Pending Shipment | 支付完成等待商家发货 |
| 快照  | Snapshot         | 下单时复制的信息副本 |

## 四、常见错误与检查清单

### 容易犯的错误

1. **把数据库设计当成领域模型**：在实体上加 `id`（自增主键）、`create_time`——这些是数据建模的事
2. **遗漏值对象**：把所有概念都建模为实体，模型过重
3. **聚合太大**：把整个订单上下文所有实体放在一个聚合里 → 性能问题
4. **跨聚合直接引用**：Order 直接引用 Product 实体而非 ProductId → 耦合
5. **忘记不可变性**：值对象应该有 setter → 违反 DDD

### 完成后的自检清单

- [ ] 所有实体有业务标识（不是数据库 ID）
- [ ] 值对象与实体区分明确
- [ ] 聚合边界合理（小聚合，不影响并发）
- [ ] 每个聚合有明确的聚合根
- [ ] 不变量在聚合边界内可保证
- [ ] 领域服务只包含跨实体的业务规则
- [ ] 通用语言词汇表覆盖所有核心业务概念
- [ ] UML 类图与文字模型一致
