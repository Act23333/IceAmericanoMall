# 08 — 行为建模方法

## 一、目的与产出

**本阶段解决什么问题**：针对复杂业务流程（如下单、支付、退款），用时序图和状态机描述对象间的交互顺序和状态流转，发现并发、事务、异常处理问题。

**输入**：API Specification（端点） + Domain Model（聚合/实体） + 用例描述（主流程）

**输出**：
- 时序图 (Sequence Diagram) — 服务间/对象间交互
- 状态机 (State Machine Diagram) — 订单/支付等有明确状态流转的实体
- 活动图 (Activity Diagram) — 复杂分支的业务流程（按需）

**产物文档类型**：UML 2.5 Sequence Diagram + State Machine Diagram

## 二、方法论步骤

### 步骤 1：确定需要建模的流程

不是所有流程都需要行为建模。筛选标准：
- **跨服务交互**（涉及 2+ 微服务）
- **状态流转复杂**（超过 3 个状态，有并发风险）
- **时序要求严格**（如支付回调的先后顺序）

### 步骤 2：绘制时序图

**核心元素**：
- 生命线 (Lifeline)：参与交互的对象/服务
- 消息 (Message)：同步/异步调用
- 激活条 (Activation)：方法执行期间
- 返回 (Return)：响应返回

**绘制步骤**：
1. 列出所有参与者（用户、前端、各服务、外部系统）
2. 按时间顺序画出消息传递
3. 标注关键数据（Token、订单号、支付单号）
4. 标注并发/锁/事务边界

### 步骤 3：绘制状态机

**适用场景**：订单、支付单、物流单（有明确生命周期的实体）

**核心元素**：
- 状态 (State)：实体在某一时刻的快照
- 转移 (Transition)：状态变化，标注触发条件
- 初始/终止状态

**示例 — 订单状态机**：
```
[初始] → 待付款 → 待发货 → 待收货 → 已完成
              ↓
           已取消
```

### 步骤 4：检查并发场景

行为建模的核心价值：发现并发问题。

- 同一订单被多次支付 → 幂等处理
- 库存同时被多个订单扣减 → 分布式锁 / 乐观锁
- 支付超时 + 用户手动取消同时触发 → 状态机互斥

## 三、冰美商城实践示例

### 下单时序图（跨服务交互）

```
用户 → 前端 → gate-service → trade-service → cart-service (获取选中商品)
                                    │
                                    ├── item-service (查库存/锁库存)
                                    ├── user-service (获取地址)
                                    ├── 生成订单 (待付款)
                                    ├── cart-service (清购物车)
                                    └── pay-service (创建支付单)
                                         │
                                         └── 返回二维码/支付链接 → 用户
```

完整时序图见项目 drawio 目录下的时序图文件

### 订单状态机

| 状态 | 编码 | 允许的下一状态 | 触发事件 |
|------|------|-------------|---------|
| 待付款 | 1 | 待发货(2), 已取消(5) | 支付成功, 取消/超时 |
| 待发货 | 2 | 待收货(3) | 商家发货 |
| 待收货 | 3 | 已完成(4) | 用户确认收货 |
| 已完成 | 4 | 待评价(6) | — |
| 已取消 | 5 | — (终态) | — |
| 待评价 | 6 | — (终态) | — |

## 四、常见错误与检查清单

### 容易犯的错误

1. **遗漏异常路径**：只画了成功流程，备选/异常流程没有
2. **时序图缺少外部系统**：忘记画支付网关、短信服务等次 Actor
3. **状态机有「死状态」**：进入后无法转移也没有终态标记
4. **忽略并发**：没有标注锁/事务边界

### 完成后的自检清单

- [ ] 时序图覆盖了正常 + 至少 2 个异常路径
- [ ] 跨服务交互在图中明确标注
- [ ] 状态机收录所有状态（含终态），无遗漏
- [ ] 并发场景有锁/幂等标注
- [ ] 与 API Spec 描述的流程一致

### 本阶段完成定义 (DoD)

- [ ] 行为模型通过评审
- [ ] 所有检查清单项通过
- [ ] 时序图与 Phase 6 (API Spec) 的端点调用链一致
- [ ] 状态机与 Phase 2 (事件风暴) 的领域事件流程一致
