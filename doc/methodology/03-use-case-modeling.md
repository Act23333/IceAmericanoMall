# 03 — 用例建模方法

## 一、目的与产出

**本阶段解决什么问题**：将 PRD 中的功能列表转化为结构化的用例模型，明确系统边界、参与者及其与系统的交互方式。

**输入**：PRD（用户角色 + 功能列表）

**输出**：

- 用例图 (Use Case Diagram)
- 用例描述（主流程 + 备选流程 + 前置/后置条件）

**产物文档类型**：UML 2.5 Use Case Diagram + Use Case Description

---

## 二、方法论步骤

### 步骤 1：识别 Actor（参与者）

从 PRD 的角色列表中提取。Actor 分为两类：

- **主 Actor**：主动发起用例的人（用户、管理员）
- **次 Actor**：响应系统请求的外部系统（支付网关、短信服务）

### 步骤 2：识别 Use Case（用例）

原则：

- 每个用例代表一个**完整的、有意义的业务目标**
- 用例名称用**动宾短语**（「浏览商品」而非「商品浏览」）
- 避免将步骤拆成用例（「输入密码」「点击登录」不是用例，它们是登录流程中的步骤）
- 内部实现机制不是用例（人机验证、加密是约束/补充规则）

### 步骤 3：建立关系

| 关系             | 符号     | 含义   | 示例                   |
| -------------- | ------ | ---- | -------------------- |
| 包含 <<include>> | 箭头→被包含 | 必须执行 | 「登录」 include 「人机验证」  |
| 扩展 <<extend>>  | 箭头→被扩展 | 条件触发 | 「首次登录奖励」 extend 「登录」 |

### 步骤 4：编写用例描述

每个用例至少包含：

```markdown
**用例名称**: 注册
**参与Actor**: 游客（主）、短信服务（次）
**前置条件**: 用户未登录
**后置条件**: 用户创建成功，返回 Token
**主流程**:
  1. 用户输入手机号
  2. 系统发送短信验证码
  3. 用户输入验证码 + 密码
  4. 系统校验验证码，创建用户，返回 Token
**备选流程**:
  2a. 手机号已注册 → 提示「手机号已注册」
  3a. 验证码错误 → 提示错误，允许重试（最多 3 次）
  3b. 60 秒内重复发送 → 拒绝，提示「请稍后再试」
```

## 三、冰美商城实践示例

### 用例图核心结构

**Actor**：

- 游客 → 浏览商品、注册、搜索
- 普通用户 → 登录、下单、支付、管理地址、签到
- 商家 → 发布商品、处理订单、发货
- 管理员 → 管理用户、管理商家、管理商品、查看统计
- 第三方系统 → 支付回调、短信发送

### 关键用例描述示例

**用例：下单**

- **Actor**：普通用户
- **前置**：已登录，购物车有选中商品，已选地址
- **主流程**：确认订单 → 扣库存 → 生成订单（待付款）→ 清购物车
- **备选**：库存不足 → 提示；超时未支付 → 取消

完整用例图见项目 drawio 目录下的用例图文件

## 四、常见错误与检查清单

### 容易犯的错误

1. **把步骤当用例**：「输入用户名」不是用例，「登录」才是
2. **用例名称用名词**：应该是动宾短语
3. **Include 箭头方向搞反**：箭头指向被包含的用例
4. **遗漏次 Actor**：支付回调、短信发送等外部系统交互

### 完成后的自检清单

- [ ] 每个 Actor 至少关联一个用例
- [ ] 每个 MVP 功能都有对应的用例
- [ ] Include/Extend 关系正确
- [ ] 核心用例有完整描述（主流程 + 备选流程）
- [ ] 用例图与 PRD 功能列表一致

### 本阶段完成定义 (DoD)

- [ ] 用例图通过团队评审
- [ ] 所有检查清单项通过
- [ ] 与 Phase 1 (PRD) 和 Phase 2 (事件风暴) 的输出一致
- [ ] 产出已同步到用例图文件（drawio 格式）
