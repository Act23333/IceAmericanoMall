# 07 — 数据建模方法

## 一、目的与产出

**本阶段解决什么问题**：将领域模型（概念模型）转化为可落地的数据库表结构（物理模型），但保持两套模型的独立性。

**输入**：Domain Model（实体 + 属性 + 关系 + 聚合）

**输出**：
- 数据库设计约定文档
- ER 图 (Entity-Relationship Diagram)
- 表定义（字段/类型/约束/索引/外键）
- 数据隔离规则（DO / DTO / VO）

**产物文档类型**：Data Model Document (ER图参考 IDEF1X / IE 表示法)

## 二、方法论步骤

### 步骤 1：建立设计约定

在开始建模前，先定好规则：

| 约定 | 说明 |
|------|------|
| 主键策略 | 见下方「主键决策」 |
| 金额存储 | INT，单位「分」 |
| 布尔值 | TINYINT (1/0) |
| 审计字段 | 每表必有 create_time + update_time |
| 快照模式 | 订单相关数据下单时复制快照 |
| 乐观锁 | 并发写入热点表使用 `version` INT + 应用层乐观锁 |
| 字符集 | utf8mb4 + utf8mb4_unicode_ci |
| 扩展性 | JSON 列预留灵活性 |

**主键决策：判断原点——业务是否需要看到和使用这个标识。**

```
业务需要看到？
  ├── 是 → 需要可读/可排序/有规则？
  │         ├── 是（客服报单号、支付对账） → id + 独立业务流水号（xxx_no）
  │         └── 否（仅需唯一引用，如分享链接） → id + 业务标识（xxx_id，雪花/UUID）
  └── 否 → 仅技术主键 id
```

| 场景 | 主键方案 | 电商示例 |
|------|---------|---------|
| 业务需要看到 + 可读可排序 | `id` + `xxx_no`（独立流水号） | 订单号、支付单号 |
| 业务需要看到 + 仅需唯一引用 | `id` + `xxx_id`（雪花/短UUID） | 用户ID、商品ID、SKU编码 |
| 业务不需要看到（子实体/关联表/内部表） | 仅 `id` | 订单项、购物车、类目、地址 |
| 现代轻量项目，无客服/对账场景 | 雪花ID直出，不额外维护编号 | 抖音订单号、美团外卖单号 |

### 步骤 2：实体 → 表映射

从领域模型的实体出发，映射为数据库表。关键差异：

| 领域模型 | 数据模型 |
|---------|---------|
| 业务标识 (如 userId) | 技术主键 id (BIGINT AUTO_INCREMENT) |
| 业务类型 (如「金额」) | 具体类型 (INT，单位为分) |
| 关联关系 | 外键 + 中间表 |
| 聚合（概念包含） | CASCADE 外键（组合关系） |

### 步骤 3：确定字段类型

- 字符串类：VARCHAR(N)，N 根据业务预估 + 20% 余量
- 枚举类：TINYINT + 注释标注枚举值
- 日期类：DATETIME（不是 TIMESTAMP，避免 2038 问题）
- 金额类：INT（不是 DECIMAL，更不是 FLOAT）
- 长文本：TEXT
- 扩展字段：JSON

### 步骤 4：设计索引

- 主键索引：默认
- 唯一索引：业务标识列、登录账号列
- 普通索引：高频 WHERE 条件（如 status, user_id, seller_id）
- 联合索引：高频组合查询（如 user_id + sku_id）
- 不滥用：每加一个索引都增加写成本

### 步骤 5：建立数据隔离规则

```
Entity (DO) → Mapper 层使用，禁止外泄
DTO         → Service 层使用，Controller 入参
VO          → Controller 返回给前端
FeignDTO    → 服务间 Feign 调用
```

## 三、冰美商城实践示例

### 设计约定应用

- 金额：`balance INT NOT NULL DEFAULT 0 COMMENT '余额（分）'`
- 快照：orders 表的 `receiver_name/phone/address` 字段均为下单时快照
- 主键策略：业务需要看到的表（user、product、orders）有业务标识；内部表（address、order_item、cart）仅技术主键

### 核心表关系

```
user ─1:N─ address
user ─1:1─ seller ─1:N─ product ─1:N─ sku
user ─1:N─ orders ─1:N─ order_item (快照SKU)
orders ─1:1─ pay_order (通过 order_no 关联)
orders ─1:1─ order_logistics
user ─N:M─ sku (经由 cart 表)
```

## 四、常见错误与检查清单

### 容易犯的错误

1. **金额用浮点**：`DECIMAL(10,2)` 或 `FLOAT` → 精度问题，应用 INT（分）
2. **地址用外键引用**：下单后用户改了地址 → 历史订单地址也变了 → 必须用快照
3. **枚举用 VARCHAR**：浪费空间，查错困难 → 用 TINYINT + 注释
4. **每个表都加业务ID（过度设计）**：业务看不到的内部表（子实体、关联表）不需要业务ID，加一个唯一的 VARCHAR 索引纯属浪费
5. **该加业务ID的不加**：API 暴露技术主键 → 外部可推算数据规模；用户分享链接里带自增 ID → 不安全
6. **订单号用纯数字雪花ID无格式**：客服场景下，"1745789123456789012" 比 "20260529123450001" 更容易报错
7. **每个字段都建索引**：盲目加索引 → 写性能下降，存储膨胀
8. **DO 直接返回给前端**：密码哈希值泄露风险 → 必须用 VO 隔离

### 完成后的自检清单

- [ ] 业务需要看到的表，有业务标识（`xxx_id` 或 `xxx_no`）；不需要的，仅技术主键即可
- [ ] 金额字段均为 INT（分）
- [ ] 订单相关快照字段已覆盖
- [ ] 索引与查询模式匹配（不是盲目全加）
- [ ] 外键级联策略正确（CASCADE vs RESTRICT vs SET NULL）
- [ ] 字符集为 utf8mb4
- [ ] ER 图与领域模型一致（不矛盾）
- [ ] DDL 脚本可重复执行（DROP IF EXISTS + CREATE）

### 本阶段完成定义 (DoD)

- [ ] 数据模型通过后端/DBA 评审
- [ ] 所有检查清单项通过
- [ ] 表结构与 Phase 5 (领域模型) 的实体一一对应
