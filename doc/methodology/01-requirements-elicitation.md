# 01 — 需求捕获方法

## 一、目的与产出

**本阶段解决什么问题**：将用户模糊的原始需求（一段话）转化为结构化的功能清单和用户角色。

**输入**：用户原始需求（自然语言描述）

**输出**：

- 用户角色定义（Actor）
- 功能点分类列表（按模块组织）
- 功能优先级划分（MoSCoW：Must/Should/Could/Won't）

**产物文档类型**：PRD (Product Requirements Document)，参考 IEEE 830 SRS

---

## 二、方法论步骤

### 步骤 1：提取名词和动词

从原始需求中：

- **名词** → 可能是实体、角色、概念
- **动词** → 可能是功能点、用户行为

**示例**：

> "我想做一个电商平台，用户能注册登录、浏览商品、加入购物车、下单支付。后台管理员能管理商品和订单。"

| 名词  | 类型  | 动词    | 功能        |
| --- | --- | ----- | --------- |
| 用户  | 角色  | 注册、登录 | 用户注册、用户登录 |
| 商品  | 实体  | 浏览    | 商品浏览      |
| 购物车 | 实体  | 加入    | 加入购物车     |
| 订单  | 实体  | 下单    | 创建订单      |
| 支付  | 行为  | 支付    | 支付处理      |
| 管理员 | 角色  | 管理    | 商品管理、订单管理 |

### 步骤 2：识别并细化角色

| 角色        | 描述      | 典型目标          |
| --------- | ------- | ------------- |
| **游客**    | 未登录用户   | 浏览商品、搜索、查看详情  |
| **普通用户**  | 已注册登录用户 | 下单、支付、管理地址    |
| **商家**    | 拥有店铺的用户 | 管理商品、处理订单     |
| **管理员**   | 平台运营    | 管理用户/商家/商品/订单 |
| **第三方系统** | 外部服务    | 支付回调、短信发送     |

### 步骤 3：按模块组织功能点

将功能点按业务模块分类，形成树状结构。每个模块从粗到细拆解。

### 步骤 4：MoSCoW 优先级划分

| 优先级             | 含义               | 示例          |
| --------------- | ---------------- | ----------- |
| **M**ust (必有)   | MVP 必须包含，否则产品不可用 | 注册/登录、下单、支付 |
| **S**hould (应有) | 重要但有替代方案         | 多级分类、优惠券    |
| **C**ould (可有)  | 锦上添花             | 积分商城、签到     |
| **W**on't (暂不)  | 明确不做（这期）         | 小程序、客服系统    |

### 步骤 5：编写 BDD 验收场景

核心流程必须写 Given-When-Then：

```gherkin
Feature: 用户注册
  Scenario: 成功注册
    Given 手机号未被注册
    And 验证码有效
    When 用户提交注册请求
    Then 创建用户记录
    And 返回 JWT Token
```

## 三、冰美商城实践示例

### 原始需求

> "我想做一个叫 IcedAmericanoMall 的电商平台，要支持电脑网页、手机 App 和小程序。用户能注册登录、浏览商品、加入购物车、下单支付。后台管理员能管理商品和订单。后续还打算做促销活动、优惠券。"

### 提取后的产出

**角色**：游客、普通用户、商家、管理员、第三方系统（支付网关/短信/OSS）

**功能模块**（精简版，完整版见 project-docs/01-PRD.md）：

| 模块  | 核心功能            | MVP      |
| --- | --------------- | -------- |
| 用户  | 注册/登录/个人中心/地址管理 | ✅        |
| 商品  | 分类/列表/详情/搜索     | ✅        |
| 购物车 | 添加/修改/删除/选中     | ✅        |
| 订单  | 创建/支付/取消/确认收货   | ✅        |
| 商家  | 商品管理/订单处理/发货    | ✅        |
| 管理员 | 用户管理/商品管理/数据统计  | ✅        |
| 积分  | 签到/任务/积分商城      | 🔵 V1.1  |
| 营销  | 优惠券/秒杀/拼团       | 🔵 V1.2+ |

详见：[project-docs/01-PRD.md](../../project-docs/01-PRD.md)

## 四、常见错误与检查清单

### 容易犯的错误

1. **角色遗漏**：只定义了「用户」和「管理员」，忽略了「未登录用户」「第三方系统」
2. **功能粒度不均**：有的功能拆到「点击按钮」级别，有的功能停留在「用户管理」级别
3. **MVP 范围模糊**：所有功能都标 Must，没有真正的优先级取舍
4. **NFR 空洞**：写「高并发」「高可用」但没有量化指标

### 完成后的自检清单

- [ ] 覆盖了所有用户角色（至少：游客/用户/商家/管理员/外部系统）
- [ ] 功能按模块组织，粒度适中（每个功能是一个独立的用户目标）
- [ ] MVP 与非 MVP 有明确边界
- [ ] 核心流程有 BDD Given-When-Then 场景（至少 1 正常 + 1 异常）
- [ ] NFR 有量化指标（TPS/延迟/可用率）

### 本阶段完成定义 (DoD)

- [ ] 产出文档通过团队评审
- [ ] 所有检查清单项通过
- [ ] 与前序阶段的可追溯性已验证
- [ ] 产出已同步到 project-docs/01-PRD.md

## 五、与后续阶段的衔接

- **输出到 Phase 2 (事件风暴)**：功能列表 → 领域事件候选项
- **输出到 Phase 3 (用例建模)**：角色清单 → Actor，功能列表 → Use Case 候选
- **输出到 Phase 6 (接口设计)**：功能列表 → API 端点目录
- **输出到 Phase 11 (开发执行)**：BDD 场景 → 集成测试

**方法论对应**：

- 本阶段 → **BDD** (验收场景是 BDD 的核心输入)
- 下一阶段 → 事件风暴 (从需求到领域的桥梁)
