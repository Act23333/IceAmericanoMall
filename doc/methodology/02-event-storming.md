# 02 — 事件风暴方法 (Event Storming)

## 一、目的与产出

**本阶段解决什么问题**：在需求分析和领域建模之间建立桥梁。通过事件风暴工作坊，快速发现领域事件、命令、聚合，识别业务热点和瓶颈，为 DDD 战术设计提供直接输入。

**输入**：PRD（用户角色 + 功能列表 + BDD 场景）

**输出**：

- 领域事件列表 (Domain Events) — 橙色贴纸
- 命令列表 (Commands) — 蓝色贴纸
- 聚合候选 (Aggregate Candidates) — 黄色贴纸
- 限界上下文边界确认 — 黑色粗线
- 热点标注 (Hotspots) — 紫色贴纸
- 读模型 (Read Models) — 绿色贴纸

**产物文档类型**：Event Storming Board (物理白板或 Miro/Mural) + 事件清单

**参考**：Alberto Brandolini "Introducing Event Storming"

---

## 二、方法论步骤

### 步骤 1：Big Picture（全景探索）— ~30min

**只贴** 领域事件（橙贴纸），按时间线从左到右排列。

- 格式：**动词过去式 + 名词**（表示已发生的事实）
- 例如：「订单已创建」「支付已完成」「商品已发货」
- 不加筛选、不讨论对错，全量贴出，形成端到端流程全貌

### 步骤 2：Pictured（结构化）— ~60min

纵向按「泳道」组织事件，每个泳道对应一个潜在限界上下文：

```
用户上下文 │ 注册已完成 → 登录已完成 → 地址已添加
商品上下文 │ 商品已发布 → 库存已扣减 → 商品已下架
订单上下文 │ 订单已创建 → 订单已支付 → 订单已发货 → 订单已签收
支付上下文 │ 支付已发起 → 支付已回调 → 退款已处理
```

**此时识别热点** — 如果两个泳道之间有大量跨上下文事件，可能是上下文划分需要调整的信号。

### 步骤 3：Command & Aggregate（命令与聚合）— ~45min

为每个事件添加：

- **Command（命令/蓝贴纸）**：谁触发了这个事件？用户操作？定时任务？外部回调？
- **Aggregate（聚合/黄贴纸）**：处理命令并产生事件的领域对象

```
命令(蓝)      聚合(黄)     事件(橙)
────────     ──────      ─────────
提交订单  →    Order   →  订单已创建
确认支付  →    Payment →  支付已完成
商家发货  →    Order   →  订单已发货
```

### 步骤 4：Read Model & External System — ~30min

- **读模型（绿贴纸）**：用户在触发命令前需要看到什么？（如「购物车页面」「订单列表」）
- **外部系统（粉贴纸）**：哪些交互涉及第三方？（如「微信支付」「阿里云短信」）

### 步骤 5：热点收口与问题清单 — ~15min

所有紫色热点贴纸整理为问题清单，逐一确认后进入领域建模。

## 三、冰美商城实践示例

### 事件风暴产出（核心流程：下单支付）

按时间线排列的领域事件：

```
注册已完成 → 登录已完成 → 商品已浏览 → 商品已加入购物车
    → 订单已创建 → 支付已发起 → 支付已回调(成功/失败)
        → [成功] 订单已确认 → 订单已发货 → 订单已签收 → 订单已完成
        → [失败] 订单已取消 → 库存已释放
```

### 聚合候选识别

| 命令 | 聚合 | 领域事件 | 限界上下文 |
|------|------|---------|-----------|
| 提交注册表单 | User | 注册已完成 | 认证 |
| 提交登录凭证 | User | 登录已完成 | 认证 |
| 加入购物车 | Cart | 商品已加入购物车 | 购物车 |
| 提交订单 | Order | 订单已创建 | 交易 |
| 发起支付 | Payment | 支付已发起 | 支付 |
| 接收回调 | Payment | 支付已回调 | 支付 |
| 确认发货 | Order | 订单已发货 | 交易 |
| 确认收货 | Order | 订单已签收 | 交易 |

### 热点清单

| 热点 | 影响范围 | 澄清结果 |
|------|---------|---------|
| 库存扣减时机：下单还是支付后？ | 订单/商品 | → 下单时预扣，支付后确认 |
| 支付超时订单如何处理？ | 订单/支付 | → 30min定时取消，释放库存 |
| 退款是逆向支付还是正向转账？ | 支付 | → 逆向支付（原路退回） |

## 四、常见错误与检查清单

### 容易犯的错误

1. **事件用将来时**：「用户将下单」→ 应为「订单已创建」（事件是已发生的事实）
2. **事件粒度太细**：「用户已输入密码」「用户已点击按钮」→ UI 行为不是领域事件
3. **跳过 Big Picture 直接建模**：先拉通端到端流程，否则容易过早陷入局部细节
4. **把 Read Model 当成事件**：「订单列表页面已加载」→ 读模型是视图不是事件
5. **热点没人跟进**：紫贴纸贴了但最后没转化成需求澄清或 ADR

### 完成后的自检清单

- [ ] 事件覆盖所有核心业务流程（正常 + 异常 + 终态）
- [ ] 事件用过去式命名（「已完成」「已取消」）
- [ ] 每个事件有对应的命令和聚合
- [ ] 限界上下文边界明确（泳道清晰，跨上下文事件有通信策略）
- [ ] 所有热点已转化为问题清单并指派负责人

### 本阶段完成定义 (DoD)

- [ ] 事件风暴产出（事件清单 + 聚合候选 + 泳道图）通过团队评审
- [ ] 所有热点有明确结论或转化为 ADR
- [ ] 限界上下文边界与 Architecture Document 一致
- [ ] 聚合候选清单已输出给领域建模阶段（Phase 5）

## 五、与后续阶段的衔接

- **输出到 Phase 3 (用例建模)**：命令 → 用例候选
- **输出到 Phase 4 (架构设计)**：限界上下文泳道 → 微服务拆分依据
- **输出到 Phase 5 (领域建模)**：聚合候选 → 实体/值对象/聚合根识别
- **输出到 Phase 10 (测试策略)**：领域事件 → 集成测试验证断点
