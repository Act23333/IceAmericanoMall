# 05.行为建模

## 文档概述

本文档属于软件项目整体分析流程的第五环节：**行为建模**。
前置依赖：需求捕获 → 用例建模 → 领域建模 → 数据建模；
后置输出：为接口设计、业务代码开发提供流程依据，对齐阿里、字节、京东通用后端设计实践，用于描述系统内部对象交互、业务流转逻辑，弥补用例图只描述“做什么”，不描述“怎么做”的短板。

> 用例建模回答：角色可以使用哪些功能；
> 行为建模回答：执行该功能时，系统内部各组件/对象按照什么顺序交互、异常场景如何处理。

## 1. 行为建模目的

针对系统内复杂业务流程（下单、退款、库存扣减、登录鉴权、订单取消等核心链路），描述对象之间交互顺序、流转分支、异常回滚逻辑。
不关注数据库表如何存储，重点关注**业务执行过程、消息流转、对象调用时序、分支条件**。

通过行为建模提前识别事务边界、并发问题、异常分支、超时处理，避免编码阶段才发现业务逻辑漏洞。

## 2. 输入与产出物

### 输入（前置阶段交付物）

1. 用例建模：用例图、用例规约（主流程、备选异常流程）
2. 领域建模：UML领域类图，业务实体、领域对象
3. 数据建模：ER图，核心数据表与约束
4. 业务规则：需求捕获阶段输出的业务规则、约束条件

### 标准产出物（互联网大厂通用实践）

| 产出物                      | 适用场景                                   | 阿里/字节京东选型建议             |
| ------------------------ | -------------------------------------- | ----------------------- |
| UML时序图（Sequence Diagram） | **对象之间消息调用、接口调用、跨模块交互**，比如下单、支付回调，优先使用 | ✅推荐核心业务必画，重点链路标配        |
| UML活动图（Activity Diagram） | 业务流程分支、判断、流转、多分支业务，例如退款审核流程、状态机流转      | ✅适合状态流转多的业务，按需选用        |
| 状态机图（状态图）                | 实体状态发生变更，例如订单：待支付→已支付→已发货→已完成→已取消      | 电商类项目强烈推荐，订单、库存、退款等核心实体 |

> 大厂实践：**不要全量绘制所有流程**。普通简单功能（修改密码、查询个人信息）无需行为建模；只针对高复杂度、高风险、涉及多组件调用、存在异常/回滚的核心业务链路建模，避免文档臃肿失效。

## 3. 两种核心图的使用规范

### 3.1 时序图（推荐优先使用）

#### 作用

表达**参与者、前端、后端服务、领域对象、第三方组件之间消息调用的先后顺序**，体现时间维度交互。

> 典型场景：用户下单、支付回调、商品库存扣减。

#### 绘制要点（参考阿里设计文档规范）

1. 纵向代表**时间顺序**，从上往下执行；横向为各个参与对象（前端、用户、Controller、Service、数据库、第三方支付、MQ消息队列）
2. 区分同步调用（实线实心箭头）、异步调用（虚线箭头/MQ事件）
3. 必须包含：正常主流程 + **关键异常分支**（库存不足、支付超时、调用失败）
4. 不要画底层数据库SQL细节，聚焦业务对象与服务交互。
5. 标注关键返回结果、事务边界。

#### 时序图文档描述模板

> 本时序图描述用户下单完整业务交互流程。参与者包含用户、前端应用、订单服务、库存服务、支付服务、消息队列。流程覆盖正常下单，以及库存不足、下单超时异常分支；当发生业务异常时执行事务回滚，释放已占用库存。

### 3.2 活动图

#### 作用

侧重业务流程流转、分支判断、条件分支、并行处理，类似业务流程图。
适合：审批流、多条件判断业务。

#### 绘制要点

1. 起始节点、结束节点；菱形代表条件判断分支。
2. 重点体现业务分支，不纠结对象调用细节。

### 3.3 状态机图（电商平台重点）

针对有大量状态流转的实体，例如订单、退款单。
明确每一个状态允许流转到哪些状态，禁止非法状态跳转，规避脏数据。

> 例：订单【待支付】可以流转为【已取消】、【已支付】；不能直接跳转到【已完成】。

## 4. 建模实施步骤（通用流程）

1. **筛选核心链路**：从用例规约中筛选高风险、多组件交互的业务；简单CRUD功能跳过行为建模。
   
   > 示例电商项目候选链路：用户下单、支付回调、订单取消、退款申请。

2. **识别参与对象**：梳理流程中全部参与者，包含外部用户、前端、各个业务服务、MQ、第三方组件、领域实体对象。

3. **梳理主业务流程**：按照业务执行顺序梳理正常通路，对应用例规约的基本流程。

4. **梳理异常/备选流程**：把用例规约中全部备选流程、失败场景补充进去，包含超时、参数错误、资源不足、调用失败。

5. **绘制对应UML图**：对象交互选时序图；流程分支多选活动图；实体状态多变补充状态机图。

6. **评审校验**：对照领域模型、业务规则校验，确认不存在逻辑冲突；标记事务、异步事件、补偿逻辑。

7. **归档维护**：业务迭代变更时同步更新行为建模图，避免文档与代码脱节。

## 5. 大厂实践经验（阿里/字节/京东设计参考）

1. **拒绝过度建模** 简单查询、修改个人信息这类简单功能，不需要绘制时序图/活动图。只针对核心链路建模，文档重在服务开发，不是为了画图。

2. **重视异常和补偿逻辑** 很多人只画成功流程，忽略失败分支。阿里开发规范要求：**时序图必须覆盖关键异常场景**，明确失败之后如何回滚、补偿、告警。例如下单失败释放库存、分布式事务补偿。

3. **区分同步与异步** 涉及消息队列MQ、异步通知，在时序图中明确标记异步调用，不要全部画成同步调用，贴合真实系统架构。

4. **和其他设计文档联动**
- 时序图中出现的接口，后续在【06.接口设计】文档定义API；

- 状态机图状态，要和数据库ER图中对应实体的状态字段严格对齐；

- 业务逻辑必须和用例描述、领域模型保持一致，不能出现逻辑矛盾。
5. **文档落地原则** 行为建模图是开发的参考，不需要做到100%和代码逐行对应，保证业务逻辑、流转顺序准确即可。

## 7. 文档示例（文字描述，可直接用于项目文档）

> 以电商下单业务举例：
> 针对用户下单这一核心用例，开展行为建模。本业务涉及用户、前端、订单服务、库存服务、消息队列多个对象。
> 使用时序图描述完整交互时序，包含正常下单流程；同时覆盖库存不足、请求超时等异常场景，出现异常执行库存补偿回滚。
> 使用订单状态机图约束订单实体全部合法状态流转，避免产生非法订单状态。
> 该行为建模结果指导后续接口设计以及业务代码开发，保证下单链路逻辑严谨。

## 8. 后续工作

行为建模完成后，进入 **06.接口设计**阶段。
基于时序图中各个服务之间的调用关系，定义RESTful API接口，确定请求路径、请求参数、响应体、错误码，输出接口文档。

## 附录：常见踩坑清单

1. ❌只画成功流程，完全忽略异常、失败场景
2. ❌把简单CRUD全部绘制时序图，文档冗余没有重点
3. ❌混淆时序图和活动图：时序图看重对象调用顺序；活动图看重业务分支流转
4. ❌状态流转和数据库表状态字段不一致
5. ❌把底层SQL数据库细节大量画进时序图，淹没业务逻辑
