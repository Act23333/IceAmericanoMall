# Spring 对 ASM 的取舍逻辑（核心就一句话）

**ASM 本身是高性能字节码工具，Spring 从来没否定它，只是「分场景用」：

性能刚需的地方就内置安全使用；非性能刚需、只启动执行一次的地方，就用标准 Java 方案换稳定性，杜绝依赖风险。**

---

## 1. 为什么参数名解析改用 DefaultParameterNameDiscoverer（反射），不用 ASM？

- 这个操作**只在 Spring 启动时执行一次**，运行时完全不跑，ASM 再快也体现不出优势
- 老式 ASM 方案需要外部依赖，容易**版本冲突、JDK 兼容差、编译参数不匹配就拿不到参数名**
- Java8+ 提供了**官方标准的 `-parameters` 编译参数**，反射就能直接拿参数名，无依赖、更稳定
- Spring 弃用的不是 ASM 技术，而是 **“为了无关紧要的速度，引入工程风险”** 的做法

## 2. 为什么 AOP、事务还在用 CGLIB，底层依然依赖 ASM？

- 动态代理需要**运行时快速生成代理类字节码**，属于**性能刚需场景**，ASM 速度无可替代
- Spring 早已把 ASM **内置重打包**（包名改为 `org.springframework.asm`），和外部依赖完全隔离
- 没有版本冲突、没有依赖传递，既保留了 ASM 的高性能，又规避了工程风险
- 这是 AOP / 事务代理的最优解，所以一直保留

## 3. Javassist 又是什么定位？

- Javassist 不是 “和 ASM 一样不好”，而是**易用但性能弱于 ASM**
- 适合 MyBatis、Hibernate 这类对字节码生成速度不敏感的场景
- 不适合 Spring 动态代理，因为代理生成对速度有要求，Spring 不会替换成它

---

# 最终极简结论

1. **ASM 快，但不是所有地方都要用**
2. **启动一次性工作 → 求稳用标准反射**
3. **运行时代理生成 → 求快用内置 ASM+CGLIB**
4. **Javassist 是另一种字节码工具，各有适用场景，并非不好**
5. Spring 所有选择，都是在**性能、稳定性、工程依赖安全**之间做平衡
