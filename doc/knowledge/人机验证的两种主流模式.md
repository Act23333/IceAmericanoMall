人机验证的集成方式确实有两种主流模式，您的疑问恰好点出了它们的设计差异。下面我分别说明，并解释为什么在发送验证码接口中，将人机验证作为流程的一部分（而非独立接口）更常见。

---

## 一、两种集成模式

### 1. 模式一：独立校验接口
- **流程**：
  1. 前端先调用后端的一个专用接口（如 `/api/captcha/verify`），传入人机验证凭证。
  2. 后端校验凭证，返回成功/失败。
  3. 前端再拿着这个结果（或后端返回的 token）去调用业务接口（如发送验证码）。
- **优点**：
  - 业务接口可以复用同一个已验证的凭证。
  - 适合复杂业务流程中需要多次校验的场景。
- **缺点**：
  - 多一次网络请求，增加延迟。
  - 需要维护凭证的临时存储（如 Redis），增加复杂度。

### 2. 模式二：凭证随业务请求提交（推荐）
- **流程**：
  1. 前端完成人机验证，获取验证服务返回的凭证（如 `captchaTicket`）。
  2. 前端直接将凭证作为业务请求（如发送验证码）的参数提交。
  3. 后端在业务逻辑中调用验证服务校验凭证，并执行业务。
- **优点**：
  - 减少一次网络往返，接口响应更快。
  - 无需额外维护凭证状态，由验证服务保证一次性。
- **缺点**：
  - 业务接口必须包含验证凭证字段，耦合度稍高。

---

## 二、为什么大厂通常选择模式二？

- **性能优先**：减少一次 HTTP 请求，降低延迟，提升用户体验。
- **安全可靠**：验证服务本身已经保证了凭证的一次性和绑定性，后端只需在校验后继续执行即可，无需自己存储临时状态。
- **简化架构**：避免引入额外的 token 存储和过期管理。

以阿里云验证码为例，其官方文档明确推荐：**前端获取验证码凭证后，直接将其作为业务接口的参数提交，后端调用验证接口进行校验**。

---

## 三、发送验证码接口的正确设计

结合模式二，发送验证码接口的完整流程如下：

```java
@PostMapping("/code")
public Result<Void> sendCode(@Valid @RequestBody SendCodeDTO dto) {
    // 1. 调用人机验证服务校验凭证
    captchaService.verify(dto.getCaptchaTicket(), dto.getCaptchaRandstr());
    
    // 2. 业务逻辑：频率限制、生成验证码、存储 Redis、调用短信
    userService.sendSmsCode(dto.getPhone());
    
    return Result.success();
}
```

这里，**人机验证并不是一个独立接口**，而是作为发送验证码流程的第一步，由后端同步完成校验。这样既保证了安全，又保持了接口的简洁性。

---

## 四、如果业务需要多次校验，怎么办？

例如，注册接口需要同时校验短信验证码和人机验证。此时，人机验证的凭证依然可以随注册请求一起提交，后端再次调用验证服务校验。由于验证服务的凭证是一次性的，第一次使用后就会失效，因此注册接口需要**重新获取人机验证凭证**（即用户需要再次完成滑块等操作）。这符合安全预期——高风险操作需要独立的验证。

如果需要复用同一个凭证（例如在同一个页面中先发送验证码再注册），可以将凭证与用户会话绑定，但通常不建议，因为这会削弱一次性凭证的安全性。

---

## 五、总结

- 人机验证**不必设计成独立接口**，将凭证作为业务参数提交，后端统一校验是更高效、更安全的做法。
- 这样设计减少了网络往返，简化了前后端交互，且符合主流验证服务（极验、阿里云）的推荐用法。
- 后端只需将验证逻辑封装在 `CaptchaService` 中，并在需要的地方调用即可，保持了代码的清晰和复用性。

如果您希望保持完全无状态的接口设计，也可以选择独立接口模式，但请权衡额外请求带来的延迟和复杂性。在大多数电商项目中，模式二是更好的选择。
