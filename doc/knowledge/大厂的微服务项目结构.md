## 一、工程分层架构：五层隔离模型

大厂普遍采用严格的**分层架构**，将代码按职责清晰划分。以字节跳动、阿里的实践为例，典型的分层结构如下：

| 层级 | 包路径示例 | 核心职责 | 依赖规则 |
| :--- | :--- | :--- | :--- |
| **接口层 (Interface)** | `api/`, `controller/` | 处理HTTP/gRPC请求、参数校验、响应封装 | 调用 `application` 层 |
| **应用层 (Application)** | `application/`, `service/` | 业务流程编排、事务管理、CQRS命令/查询 | 调用 `domain` 和 `infrastructure` |
| **领域层 (Domain)** | `domain/` | 核心业务逻辑、实体、值对象、领域服务 | **不依赖任何外部框架** |
| **基础设施层 (Infrastructure)** | `infrastructure/`, `repository/` | 数据库、缓存、消息队列的具体实现 | 实现 `domain` 定义的接口 |
| **API契约层** | `api/proto/`, `api/swagger/` | 定义Protobuf/OpenAPI等跨语言接口规范 | 独立于业务逻辑，供调用方引用 |

### 核心约束
- **依赖方向向内**：外层依赖内层，内层不知外层。
- **领域层纯净**：`domain` 包中不使用Spring注解、不依赖数据库驱动、不进行JSON序列化，保持纯POJO + 业务逻辑。
- **CQRS读写分离**：命令（写）与查询（读）在应用层物理隔离，分别处理事务与视图。

## 二、对象与命名规范：统一语言

大厂对VO/DTO/PO等对象的定义和命名有严格标准，阿里《Java开发手册》是业界事实规范：

| 对象类型 | 命名示例 | 说明 | 所在包 |
| :--- | :--- | :--- | :--- |
| **Entity (PO)** | `UserEntity`, `OrderPO` | 与数据库表一一对应，常使用MyBatis-Plus等ORM | `repository.entity` |
| **DTO (Data Transfer Object)** | `UserDTO`, `OrderDTO` | 服务层之间传输数据，或Feign接口传输 | `application.dto` 或 `api.dto` |
| **VO (View Object)** | `UserVO`, `OrderVO` | 返回给前端展示的对象 | `controller.vo` |
| **Request/Response** | `UserCreateRequest`, `UserResponse` | 接口层的输入输出参数 | `controller.request/response` |
| **Converter** | `UserConverter` | 使用MapStruct等工具转换对象 | `common.convert` 或 `converter` |

### 命名与包结构原则
- **按业务模块分包**：`com.company.product.user/order`，而非按技术层拆分。
- **接口层独立**：Controller只依赖Request/Response，不依赖Entity。
- **禁止跨层引用**：Controller不能直接使用Entity，Service不能直接使用Request/Response。

## 三、依赖与配置管理：显式、隔离

遵循 **“十二要素应用（Twelve-Factor App）”** 方法论，这是AWS、Oracle等官方推荐的微服务开发准则：

1. **显式声明依赖**：所有依赖通过 `pom.xml` 或 `go.mod` 声明，不依赖操作系统或服务器预装环境。
2. **配置与代码分离**：配置文件（如 `application-dev.yml`）不打包进JAR，通过环境变量或配置中心（Nacos/Apollo）动态注入。
3. **无状态进程**：服务自身不存储会话状态，所有状态外置到Redis/DB。

### Maven/Gradle 多模块管理
大厂项目采用父子工程结构，在根 `pom.xml` 的 `dependencyManagement` 中统一锁定所有依赖版本（Spring Cloud Alibaba、MyBatis-Plus、MapStruct等），子模块按需引用，无需再写版本号。

## 四、代码与架构设计原则

阿里、美团等大厂推行六大设计原则作为“架构宪法”：

- **单一职责**：一个类只负责一项职责，例如 `UserService` 不应同时处理日志和通知（可通过事件解耦）。
- **开闭原则**：对扩展开放，对修改关闭。新增功能通过实现接口而非修改原有代码，如策略模式实现多种折扣计算。
- **依赖倒置**：面向接口编程，高层模块不依赖低层模块。例如 `domain` 层定义 `UserRepository` 接口，`infrastructure` 层用 `UserRepositoryImpl` 实现。

## 五、技术栈选型与演进

| 公司/场景 | 主力语言 | 核心框架/组件 | 备注 |
| :--- | :--- | :--- | :--- |
| **阿里巴巴/蚂蚁金服** | Java | Spring Cloud Alibaba (Nacos/Sentinel/Seata)、Dubbo、MyBatis-Plus | 电商、金融核心业务以Java为主 |
| **腾讯/字节跳动** | Java + Go | 接入层/网关用Go（高并发），核心领域用Java（事务/生态） | Go处理网关、流计算，Java处理订单、账户等复杂业务 |
| **Google/Uber** | Go | 自研框架，Uber有公开的Go风格指南 | 强调高并发、轻量级、云原生 |
| **Oracle/Neflix** | Java/Go | Spring Cloud Netflix (Eureka/Hystrix) | 微服务先驱，部分组件已进入维护期 |

### 混合栈趋势
大厂正推行**Go+Java混合栈**：Go用于API网关、Sidecar等高并发接入层（协程开销低、编译快），Java用于领域服务层（事务、生态成熟）。两者通过gRPC+Protobuf通信，统一治理底座。

## 总结：大厂创建项目的标准流程

1. **确定业务边界**：按领域拆分微服务（如用户、订单、商品），而非按技术层。
2. **搭建父子工程**：根项目统一管理依赖版本，子模块按层或模块划分（`api`, `service`, `repository`）。
3. **定义API契约**：先定义Protobuf/OpenAPI，再生成服务端/客户端代码，做到“契约先行”。
4. **编写领域模型**：在 `domain` 包中用纯Java/Go编写业务逻辑，不依赖框架。
5. **实现基础设施**：用适配器模式封装DB、缓存、MQ的具体实现，面向接口编程。
6. **配置自动化**：所有环境配置外置，使用Nacos或K8s ConfigMap管理。
7. **编写测试**：单元测试覆盖domain层，集成测试覆盖repository层。

遵循这套体系，项目才能具备大厂级的**可维护性、可扩展性和高并发能力**。


### 微服务架构的子功能分包结构
**微服务架构**，`user-service` 和 `order-service` 本来就是两个独立服务 →

那这句话的意思**就变了**！我给你用**微服务专属视角**讲透，一秒就懂：

---

# 核心终极结论（微服务专用）

### 你已经把「大业务模块」拆成了独立微服务：

- 用户 = `user-service`（单独项目）
- 订单 = `order-service`（单独项目）
- 商品 = `product-service`（单独项目）

### 所以：

**「按业务模块分包」这句话，在微服务里 = 每个微服务【内部】，按「子功能 / 子业务」分包，

绝对不允许把整个服务的所有 Controller 塞一个包、所有 Service 塞一个包！**

---

# 我用你的 `user-service` 举例子，一眼看懂

## ❌ 错误写法（微服务内部按「技术层」分包，老旧、混乱）

这就是**禁止的写法**：

整个用户服务，就 4 个大包，所有子业务全混在一起：

plaintext

```
user-service（用户微服务）
├── controller   ← 登录Controller、个人信息Controller、地址Controller 全堆在这里！
├── service      ← 所有业务逻辑堆一起
├── mapper       ← 所有SQL堆一起
└── entity
```

❌ 问题：

改个「收货地址」，要翻遍整个 controller /service，代码乱成一锅粥。

---

## ✅ 正确写法（微服务内部按「子业务模块」分包，大厂标准）

**用户服务内部，再按小功能拆分**：

登录是一个模块、个人信息是一个模块、收货地址是一个模块：

plaintext

```
user-service（用户微服务）
├── login        # 登录子模块（controller + service + mapper 全在这）
├── info         # 个人信息子模块
├── address      # 收货地址子模块
├── settings     # 用户设置子模块
└── config       # 全局配置
```

✅ 完美：

- 改登录 → 只动 `login` 包
- 改地址 → 只动 `address` 包
- 高内聚、不混乱、微服务标准规范

---

# 一句话翻译你最疑惑的那句话

原句：

### **按业务模块分包，而非按技术层拆分**

### 微服务版大白话：

1. **宏观上**：你已经拆成 `user / order / product` 独立微服务 ✅
2. **微观上**：**每个微服务自己内部**，要按「子功能」分包，
    
    **不要把所有 Controller 塞一个包、所有 Service 塞一个包** ❌

---

# 最终总结（你完全不用纠结了）

你是微服务，所以：

1. **不用在一个项目里分 user /order 包**（它们已经是两个服务了）
2. **只需要保证：每个微服务内部，按子功能分包**
3. **这就是大厂微服务的标准分包规则**
