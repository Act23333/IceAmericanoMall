关于用户注销后的账号复用问题，大厂通常采用“逻辑删除 + 唯一性控制”或“物理删除+历史归档”的方案，核心目的是在**保留历史数据**与**允许手机号重新注册**之间找到平衡。下面分析常见方案，并给出推荐。

---

## 一、逻辑删除的冲突点

如果只在 `user` 表中增加一个 `deleted` 字段（0=未删除，1=已删除），并在 `phone` 字段上建立唯一索引，那么：
- 用户 A 注销后，`deleted=1`，但 `phone` 仍被占用，导致新用户无法用同一手机号注册。
- 即使去掉唯一索引，业务层校验时仍需判断是否有未删除的用户（`deleted=0`），但数据库中可能存在多条 `deleted=1` 的记录（同一手机号多次注销再注册），不过一般不会这样设计，因为多次注销再注册应复用原记录或合并。

因此，逻辑删除必须与**唯一性控制**配合。

---

## 二、大厂常见处理方案

### 1. 物理删除（简单，但丢失数据）
- **做法**：用户注销时直接删除记录。
- **优点**：手机号立即释放，唯一索引无冲突。
- **缺点**：丢失用户订单、地址等历史数据，无法追溯；且用户再次注册时无法关联历史记录。
- **适用**：对历史数据不敏感的场景，如一些临时性应用。

### 2. 逻辑删除 + 业务层唯一性校验
- **做法**：保留 `deleted` 字段，但**不在 `phone` 上加唯一索引**。注册时先查询是否存在 `deleted=0` 的记录，若存在则拒绝；若只存在 `deleted=1` 的记录，可允许重新注册（更新原记录或创建新记录）。
- **优点**：数据不丢失，手机号可复用。
- **缺点**：业务层需自行保证唯一性，并发时可能产生脏数据（可通过数据库锁或分布式锁解决）；且同一个手机号可能有多条 `deleted=1` 的记录，管理混乱。
- **适用**：中小型项目，并发不高，愿意接受轻微复杂度。

### 3. 主表 + 历史归档表（推荐）
- **做法**：
  - `user` 表只存放**活跃用户**（未注销），`phone` 字段加唯一索引。
  - 用户注销时，将数据**移入** `user_archive` 表（或 `user_deleted` 表），结构相同，但无唯一索引限制。
  - 手机号释放，新用户可用原手机号注册，生成新记录。
  - 历史订单等关联数据通过 `user_id` 关联，若原用户 `id` 不再使用，则订单表需保留原 `user_id`，但新用户获得新 `id`，两者无关联。
- **优点**：
  - 主表保持简洁，手机号唯一索引有效，无需业务层额外校验。
  - 历史数据完整保留，便于审计。
  - 支持手机号立即复用。
- **缺点**：需维护两张表，注销逻辑稍复杂；需处理关联数据的归属（如订单中的用户ID不会改变）。
- **适用**：中大型项目，对数据完整性要求高，且需要手机号复用。

### 4. 用户回收站机制
- **做法**：注销后用户进入“回收站”状态（如 `deleted=1`），但手机号被**占用一段时间**（如 30 天）。期间不允许注册，超时后自动物理删除，手机号释放。
- **优点**：给用户反悔机会，防止恶意注销注册。
- **缺点**：需要定时任务清理，复杂度较高；手机号释放有延迟。
- **适用**：需要保护用户权益的平台，如社交应用。

---

## 三、推荐方案

### 对于 **IcedAmericanoMall**（多商家电商平台，MVP 阶段）
建议采用 **方案 2（逻辑删除 + 业务层唯一性校验）** 或 **方案 3（主表+归档表）**。

- **MVP 阶段**：优先采用**逻辑删除 + 业务层唯一性校验**，实现简单，快速上线。在注册接口中使用分布式锁或数据库唯一索引（注意索引方案）来避免并发冲突。同时可保留 `deleted` 字段，允许已注销手机号重新注册时，更新原记录（将 `deleted` 改回 0，并重置其他信息）。这样既保留历史，又复用原 `user_id`，确保关联数据不丢失。

- **后续迭代**：若用户量增大，需严格保证手机号唯一性且历史数据量大，可升级为**主表+归档表**方案。在用户注销时，将记录从 `user` 移到 `user_archive`，并保留 `user_id` 不变（归档表中 `user_id` 与主表共用序列），这样订单等关联数据仍能正确关联历史用户，但主表不再包含已注销用户。

### 具体实现建议（MVP 逻辑删除 + 业务校验）
1. **表设计**：
   ```sql
   CREATE TABLE `user` (
       `id` BIGINT AUTO_INCREMENT PRIMARY KEY,
       `phone` VARCHAR(20) NOT NULL,
       `deleted` TINYINT NOT NULL DEFAULT 0,
       -- 其他字段
       UNIQUE KEY `uk_phone_deleted` (`phone`, `deleted`)  -- 联合唯一索引（仅针对未删除记录？但 deleted=1 会有多条，不行）
   );
   ```
   注意：联合唯一索引 `(phone, deleted)` 无法满足 `deleted=1` 有多个的需求，因此需移除唯一索引，通过业务层控制。

2. **注册逻辑**：
   - 使用分布式锁（`lock:register:phone`）避免并发。
   - 查询 `SELECT * FROM user WHERE phone = ?`。
   - 若存在 `deleted=0` 的记录，返回“手机号已注册”。
   - 若存在 `deleted=1` 的记录，则更新该记录（将 `deleted` 置 0，并更新其他字段，如密码、注册时间等），同时重置历史数据（如订单关联仍保留原 `user_id`，这通常是合理的）。
   - 若不存在，则插入新记录。

3. **注销逻辑**：
   - 将用户记录的 `deleted` 设为 1，可同时记录注销时间。

这种方案在中等并发下足够可靠，且历史订单等关联数据仍然通过原 `user_id` 可查。

---

## 四、总结

| 方案 | 数据保留 | 手机号复用 | 实现复杂度 | 推荐阶段 |
|------|----------|------------|------------|----------|
| 物理删除 | ❌ | ✅ | 低 | 不推荐 |
| 逻辑删除+业务校验 | ✅ | ✅ | 中 | MVP |
| 主表+归档表 | ✅ | ✅ | 中高 | 成熟期 |
| 回收站机制 | ✅ | 延迟 | 高 | 特定场景 |

对于 **IcedAmericanoMall**，建议 MVP 采用**逻辑删除 + 业务层唯一性校验**（更新已注销记录的方式），既保留历史数据，又允许手机号重新注册。后续可根据业务量演进到主表+归档表。
